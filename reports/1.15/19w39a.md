# Minecraft 19w39a 变更分析

- 上一个版本：19w38b
- 当前版本：19w39a

## 铁轨按玩家朝向放置，部分连接选择保留原方向

铁轨放置时开始使用玩家的水平朝向；无法由相邻铁轨唯一决定方向时，新版会保留传入的形状。普通铁轨、动力铁轨、探测铁轨和激活铁轨都使用这一放置逻辑。

### 差异出现的场景

在没有可连接铁轨的位置放置铁轨，或在南北、东西两条轴线都有可连接铁轨的位置放置只能保持直线的铁轨。

### 版本变化

- 19w38b：孤立铁轨默认沿南北方向。对于不能转弯的铁轨，两条轴线都有候选连接时，东西方向会覆盖南北方向。
- 19w39a：玩家面向东或西时，孤立铁轨沿东西方向；面向南或北时沿南北方向。不能转弯的铁轨在两条轴线都有候选连接时，保留放置时已有的形状。

相邻连接能明确决定方向时，仍由连接规则决定最终形状。普通铁轨在岔路处依据红石信号选择弯道的规则没有随这次默认方向修改一起改变。

### 实际影响

搭建矿车装卸站、断轨和只能单独放置的短轨道时，玩家朝向开始影响矿车行驶方向；依赖默认南北朝向或交叉连接处默认东西朝向的建造步骤会产生不同结果。用 `/setblock` 在原本不是铁轨的位置放入一段指定为东西向的孤立铁轨时，旧版初次计算连接会把它覆盖为南北向，新版能够保留指定的东西向形状。

## 连接着果实的瓜茎开始掉落种子

破坏仍连接着西瓜或南瓜的瓜茎时，19w38b 不掉落任何物品；19w39a 会掉落对应种子，数量为 0～3 个，每次掉落的期望数量约为 1.6 个。新版进行三次独立判定，每次约有 53.33% 概率得到一粒种子；爆炸破坏时还会受到爆炸掉落衰减影响。

这让清理成熟瓜田、连果实一起铲除瓜茎或通过破坏瓜茎回收种子的操作能够获得种子。只收割果实并保留瓜茎的常规南瓜、西瓜农场，不会因为这张掉落表增加额外产物。

## 鹦鹉和蜜蜂的飞行寻路增加竖向斜路，并重做穿角检查

使用飞行寻路的生物会在相邻格点之间寻找路线。新版补上缺少的竖向斜向连接，并改用另一组相邻空间条件判断三轴斜路。

### 差异出现的场景

鹦鹉或蜜蜂需要一边上升、下降，一边朝一个水平方向移动，或者试图从障碍物边角斜向绕过。

### 版本变化

- 19w38b：一次寻路扩展最多考虑 18 个方向，包括六个正方向、四个水平斜方向和八个三轴斜方向；缺少“上下加一个水平方向”的八种连接。三轴斜路只检查对应的水平斜格和正上、正下格是否可通行。
- 19w39a：最多考虑完整的 26 个相邻方向，新增上述八种竖向斜路。三轴斜路改为要求对应的三个两轴斜格都可通行；其中任何一个被阻挡，就不会接受这条斜路。旧版直接检查的正上、正下格不再是独立前提，因此在三个两轴斜格都符合条件时，也存在旧版拒绝而新版接受的斜路。

### 实际影响

有高度差的通道、阶梯状障碍和笼舍入口可能得到不同的路线；原先依靠缺少竖向斜路或特定穿角检查来限制生物路线的布置，也可能失去原有限制。蜜蜂往返蜂巢和花之间的具体路线也可能变化，但这项修改本身没有给采蜜速度增加固定倍率。

## 加载后尚未恢复的拴绳信息能够再次保存

生物从存档加载后，拴绳连接会暂存为待恢复信息，再在生物更新时寻找牵引者或拴绳结。如果生物在这次恢复之前再次被保存，例如处在已加载但尚未执行实体更新的区块中：

- 19w38b：保存时只记录已经建立的牵引连接，遗漏这份待恢复信息；再次加载后会失去原有拴绳记录。
- 19w39a：尚未建立连接时，也会把待恢复信息复制到存档中，保留下一次加载后恢复连接的机会。

这影响区块加载、卸载和保存交界处的拴绳运输及动物固定。新版没有改变实际恢复时寻找牵引者的规则；牵引者找不到而无法恢复的情况仍按原规则处理。

## 徒手或使用错误工具破坏铁门不再掉落铁门

玩家在非创造模式下破坏完整铁门时，19w38b 会在移除另一半门的过程中直接结算门的掉落，没有核对工具是否能采集铁门。19w39a 加入采集资格检查：徒手或拿着不适用的工具破坏后，门消失且不掉物品；使用镐正常采集仍可获得铁门。上下半部都经过这一入口，因而两种破坏位置都受影响。

## 卫道士骑乘非地面寻路生物时不再在开门 AI 中崩溃

通过实体 NBT 让启用 AI 的卫道士骑乘使用飞行或其他非地面寻路的生物时，卫道士会使用坐骑的寻路器。19w38b 在每次 AI 更新中直接把这个寻路器当成地面寻路器，因类型不符而抛出异常。19w39a 先检查类型，只有地面寻路器才设置袭击期间的开门能力，因此这一更新入口能够继续执行。

这项修复覆盖已经建立骑乘关系后的 AI 更新；普通地面卫道士的袭击开门规则没有改变。

## 对方块使用烟花时，发射点向外移动 0.15 格

19w38b 在玩家点击方块表面的交点直接生成烟花火箭；19w39a 沿被点击面的朝外方向再偏移 0.15 格。点击顶面时更高，点击侧面时离墙更远，点击底面时更低。依赖紧贴方块表面生成火箭的布置，会得到不同的初始位置。

这个修改只发生在对方块使用烟花的入口。鞘翅飞行中在空中使用烟花所走的附着玩家入口没有这次位移修改。

## 驾驶结束后的载具位置同步以当前坐标为基准

客户端自行控制船或可骑乘生物时，会忽略服务器对这些实体的相对移动更新。19w38b 没有同时推进用于接收后续相对移动的坐标基准；如果驾驶期间载具已经离开该基准，放弃控制后收到的相对移动会从旧位置累加，造成客户端显示的载具跳回或偏离实际位置。

19w39a 在船和生物仍由本机控制时，每次更新都把这个基准同步为当前坐标，缩小控制权交还后的错误位移。它改变客户端的位置衔接，不改变船或坐骑的服务器运动速度。

玩家自身接收传送时，新版也会同步更新上一帧坐标，避免仍从传送前的位置向新位置绘制过渡；相对传送保留对应轴速度、绝对传送清除对应轴速度的规则保持不变。

## 文本可读取 storage，但直接存入队伍和记分板存在保存异常

已有的 NBT 文本组件可以从方块或实体读取数据。19w39a 增加从命令 storage 读取数据的形式，但没有同步补齐这种组件的序列化支持。

### 差异出现的场景

storage 中已经存有数据，命令需要把其中某个路径显示为 JSON 文本，例如：

```mcfunction
data modify storage demo:state message set value "测试"
tellraw @a {"nbt":"message","storage":"demo:state"}
```

### 版本变化

- 19w38b：NBT 文本的来源必须是 `block` 或 `entity`，上例的 `storage` 文本无法解析。
- 19w39a：支持 `storage` 来源，`/tellraw`、`/title` 等会先解析文本的入口可以显示对应数据；`interpret:true` 也可将取得的字符串继续作为 JSON 文本解析。

### 实际影响

数据包可以直接显示存储在 storage 中的数据，无需先复制到实体或方块。

这一快照仍只支持把 `block` 和 `entity` 两种 NBT 文本组件重新序列化。直接执行如下命令时，队伍前缀会保存尚未解析的 storage 组件：

```mcfunction
team modify example prefix {"nbt":"message","storage":"demo:state"}
```

前提是队伍 `example` 已存在。与旧版在解析阶段拒绝不同，新版会把该组件放入队伍状态，随后同步队伍数据或保存记分板时，序列化会抛出 `IllegalArgumentException`。对于保留了这一状态、仍正常启用自动保存的服务器，自动保存会沿未捕获的异常退出服务器主循环。把 storage 组件直接用作记分板显示名称也有同样的序列化缺口。

因此，这个版本中“会先解析再显示”的文本入口与“直接保留原始组件”的队伍、记分板名称入口，实际可用范围不同。

## 只检查坐标和维度的谓词不再要求目标位置已加载

位置条件用于进度和数据包谓词，也会被 `/execute if predicate` 的 `location_check` 使用。在目标区块未加载时：

- 19w38b：整个位置条件直接失败，即使只要求维度、坐标范围，甚至没有任何具体限制。
- 19w39a：只要求坐标、维度或没有具体限制时，可以正常匹配；需要读取生物群系、结构、亮度、方块或流体时，仍要求目标位置已加载。

例如把命令执行位置移到未加载区块，再检查一个只限制主世界维度的 `location_check`，新版可以通过，旧版失败。数据包若利用这一旧失败行为把普通位置条件兼作区块加载检查，结果会改变。

显式写出的空对象也有区别：`block:{}`、`fluid:{}`、`light:{}` 都会建立需要已加载位置的条件；省略这些字段才是不读取对应世界数据的无限制条件。

## JSON 文本参数和错误格式的异常处理改变

当 `/tellraw` 等命令的 JSON 文本嵌套深到使文本解析耗尽调用栈时，19w38b 会让 `StackOverflowError` 逃出这一解析入口；19w39a 将它转换为 JSON 解析异常，再由文本参数解析器返回命令语法错误。修改只覆盖通过命令字符串读取文本的这条入口，没有给所有书本、告示牌和 NBT 文本解析统一增加栈溢出保护。

如果文本使用的格式字符串包含不支持的格式占位符，例如把 `{"translate":"%d"}` 作为文本，旧版在当前语言和默认语言都无法处理时继续抛出格式异常；新版直接保留原始格式字符串显示，不再因这一格式错误抛出异常。

## 隐身生物可能失去本体的发光轮廓

给生物同时施加隐身和发光，并由无法看见其隐身本体的普通玩家观察时：

- 19w38b：轮廓单独绘制，轮廓绘制阶段强制包括隐身生物的本体，因此仍能看到身体轮廓。
- 19w39a：轮廓从正常绘制的模型复制而来，隐身本体没有进入正常绘制时，也不会产生本体轮廓。例如隐身且发光、没有其他可见附加层的未充能苦力怕，会失去旧版的身体轮廓。

装备等仍然可见的附加部分可能保留轮廓。旁观者，以及允许看见隐身队友的同队玩家，不属于上述本体被完全省略的条件。
