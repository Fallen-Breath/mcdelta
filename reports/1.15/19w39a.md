# Minecraft 19w39a 变更分析

- 上一个版本：19w38b
- 当前版本：19w39a

## 铁轨按玩家朝向放置，部分连接选择保留原方向

铁轨放置时开始使用玩家的水平朝向；无法由相邻铁轨唯一决定方向时，新版会保留传入的形状。普通铁轨、动力铁轨、探测铁轨和激活铁轨都使用这一放置逻辑。

### 差异出现的场景

在没有可连接铁轨的位置放置铁轨，或在南北、东西两条轴线都有可连接铁轨的位置放置不能转弯的铁轨。用 `/setblock` 在原本不是铁轨的位置放入指定朝向的孤立铁轨，也会经过这次连接计算。

### 版本变化

- 19w38b：孤立铁轨默认沿南北方向，命令指定的东西向也会在初次计算连接时被覆盖。不能转弯的铁轨在两条轴线都有候选连接时，东西方向会覆盖南北方向。
- 19w39a：玩家面向东或西时，孤立铁轨沿东西方向；面向南或北时沿南北方向。命令指定的孤立铁轨东西朝向能够保留。不能转弯的铁轨在两条轴线都有候选连接时，保留放置时已有的形状。

相邻连接能明确决定方向时，仍由连接规则决定最终形状。普通铁轨在岔路处依据红石信号选择弯道的规则保持不变。搭建断轨、短轨道或矿车装卸站时，原先依赖默认朝向的建造步骤会产生不同结果。

## 连接着果实的瓜茎开始掉落种子

瓜茎连接到西瓜或南瓜后会变成附着状态。新版为这种状态的瓜茎补上种子掉落。

### 差异出现的场景

破坏仍连接着西瓜或南瓜的瓜茎，包括清理瓜田和通过破坏瓜茎回收种子的操作。

### 版本变化

- 19w38b：附着状态的瓜茎不掉落任何物品。
- 19w39a：掉落对应种子，数量为 0～3 个。掉落表进行三次独立判定，每次约有 53.33% 概率得到一粒种子，未受爆炸衰减时的期望数量约为 1.6 个；爆炸破坏时还会受到爆炸掉落衰减影响。

只收割果实并保留瓜茎的常规南瓜、西瓜农场，不会因为这项修改增加额外产物。

## 徒手或使用错误工具破坏铁门不再掉落铁门

铁门由上下两半组成，玩家破坏其中一半时，还会移除另一半并处理掉落。新版在这一处理中加入工具采集资格检查。

### 差异出现的场景

玩家在非创造模式下，徒手或使用不能采集铁门的工具，破坏完整铁门的上半部或下半部。

### 版本变化

- 19w38b：移除另一半门时直接结算掉落，没有核对工具是否能采集铁门，因此仍会掉落铁门物品。
- 19w39a：工具不满足采集条件时，铁门消失且不掉落物品；使用镐正常采集仍可获得铁门。

## 对方块使用烟花时，发射点向外移动 0.15 格

玩家对方块使用烟花火箭时，火箭的生成位置由点击交点决定。新版在此基础上增加朝向方块外侧的偏移。

### 差异出现的场景

手持烟花火箭，对方块的顶面、侧面或底面使用物品。

### 版本变化

- 19w38b：火箭直接生成在玩家点击方块表面的交点。
- 19w39a：沿被点击面的朝外方向偏移 0.15 格后生成。点击顶面时更高，点击侧面时离墙更远，点击底面时更低。

依赖紧贴方块表面生成火箭的布置，会得到不同的初始位置。鞘翅飞行中在空中使用烟花走的是附着玩家的另一入口，不受这次偏移修改影响。

## 鹦鹉和蜜蜂的飞行寻路增加竖向斜路，并重做穿角检查

使用飞行寻路的生物会在相邻格点之间寻找路线。新版补上缺少的竖向斜向连接，并改用另一组相邻空间条件判断三轴斜路。

### 差异出现的场景

鹦鹉或蜜蜂需要一边上升、下降，一边朝一个水平方向移动，或者试图从障碍物边角斜向绕过。

### 版本变化

- 19w38b：一次寻路扩展最多考虑 18 个方向，包括六个正方向、四个水平斜方向和八个三轴斜方向；缺少“上下加一个水平方向”的八种连接。三轴斜路只检查对应的水平斜格和正上、正下格是否可通行。
- 19w39a：最多考虑完整的 26 个相邻方向，新增上述八种竖向斜路。三轴斜路改为要求对应的三个两轴斜格都可通行；其中任何一个被阻挡，就不会接受这条斜路。旧版直接检查的正上、正下格不再是独立前提，因此在三个两轴斜格都符合条件时，也存在旧版拒绝而新版接受的斜路。

### 实际影响

有高度差的通道、阶梯状障碍和笼舍入口可能得到不同的路线，蜜蜂往返蜂巢和花之间的具体路线也可能变化。依靠旧版缺少竖向斜路或特定穿角检查来限制生物路线的布置，可能失去原有限制。

## 加载后尚未恢复的拴绳信息能够再次保存

生物从存档加载后，拴绳连接会暂存为待恢复信息，再在生物更新时寻找牵引者或拴绳结。新版补上这份暂存信息的保存处理。

### 差异出现的场景

带有拴绳记录的生物从存档加载后，在恢复连接之前再次被保存，例如处于已加载但尚未执行实体更新的区块中。

### 版本变化

- 19w38b：保存时只记录已经建立的牵引连接，遗漏待恢复信息；再次加载后会失去原有拴绳记录。
- 19w39a：尚未建立连接时，也会把待恢复信息复制到存档中，保留下一次加载后恢复连接的机会。

这减少了区块加载、卸载和保存交界处的拴绳记录丢失。实际恢复时寻找牵引者的规则保持不变，牵引者找不到而无法恢复的情况仍按原规则处理。

## 卫道士骑乘非地面寻路生物时不再在开门 AI 中崩溃

卫道士的袭击开门 AI 会设置寻路器的开门能力。骑乘其他生物时，卫道士采用坐骑的寻路器，新版在设置前增加了寻路器类型检查。

### 差异出现的场景

通过实体 NBT 让启用 AI 的卫道士骑乘使用飞行或其他非地面寻路的生物，骑乘关系已经建立并开始执行 AI 更新。

### 版本变化

- 19w38b：直接把坐骑的寻路器当成地面寻路器，因类型不符而抛出异常。
- 19w39a：只有地面寻路器才设置袭击期间的开门能力，其他类型跳过这一步，AI 更新能够继续执行。

普通地面卫道士的袭击开门规则保持不变。

## 自定义投射物的 inGround 改按非零字节读取

`inGround` 记录投射物是否已落地。新版改用布尔方式读取该字段，使非标准字节值也能触发已落地处理，影响箭、三叉戟和继承通用投掷物逻辑的投射物。

### 差异出现的场景

使用命令或外部编辑写入 `inGround:2b`、`inGround:-1b` 等非零且不为 1 的字节值，再让投射物读取这些数据。

### 版本变化

- 19w38b：只有数值恰为 `1b` 才识别为已落地，上述自定义值均被当作未落地。
- 19w39a：任何非零字节都识别为真，按相应投射物的已落地逻辑处理。例如带有初速度的雪球会在下一次更新时清除此标记，并把三个轴的速度分别乘以小于 0.2 的随机数。

正常游戏保存的 `0b`、`1b` 不产生这项差异。

## 驾驶结束后的载具位置同步以当前坐标为基准

客户端自行控制船或可骑乘生物时，会忽略服务器对这些实体的相对移动更新。新版在控制期间同步推进相对移动使用的坐标基准，改善交还控制权时的位置衔接。

### 差异出现的场景

玩家驾驶船或可骑乘生物，使载具离开客户端原先记录的相对坐标基准；停止控制后，客户端继续接收该实体的相对移动更新。

### 版本变化

- 19w38b：控制期间没有同步推进接收相对移动的坐标基准，交还控制权后的更新可能从旧位置累加，造成客户端显示的载具跳回或偏离实际位置。
- 19w39a：船和生物仍由本机控制时，每次更新都把基准同步为当前坐标，缩小控制权交还后的错误位移。

这一修改影响客户端位置衔接，载具在服务器上的运动速度保持不变。

## 玩家传送时同步更新画面插值的起点

客户端通过上一帧坐标与当前坐标之间的插值绘制移动。新版收到玩家传送后，同时将上一帧坐标移到新位置。

### 差异出现的场景

玩家已经进入世界，随后收到服务器发来的位置传送或校正。

### 版本变化

- 19w38b：常规传送处理没有同步更新用于画面插值的上一帧坐标，画面可能仍从传送前的位置向新位置绘制过渡。
- 19w39a：将上一帧坐标直接设为传送后的位置，避免这一跨越传送距离的绘制过渡。

相对传送保留对应轴速度、绝对传送清除对应轴速度的规则保持不变。

## 文本可读取 storage，但直接存入队伍和记分板存在保存异常

已有的 NBT 文本组件可以从方块或实体读取数据。19w39a 增加从命令 storage 读取数据的形式，但没有同步补齐这种组件的序列化支持。

### 差异出现的场景

storage 中已经存有数据，命令需要把其中某个路径显示为 JSON 文本，例如：

```mcfunction
data modify storage demo:state message set value "测试"
tellraw @a {"nbt":"message","storage":"demo:state"}
```

### 版本变化

- 19w38b：NBT 文本的来源必须是 `block` 或 `entity`，上例的 `storage` 文本无法解析。
- 19w39a：支持 `storage` 来源，`/tellraw`、`/title` 等会先解析文本的入口可以显示对应数据；`interpret:true` 也可将取得的字符串继续作为 JSON 文本解析。

### 实际影响

这一快照仍只支持把 `block` 和 `entity` 两种 NBT 文本组件重新序列化。直接执行如下命令时，队伍前缀会保存尚未解析的 storage 组件：

```mcfunction
team modify example prefix {"nbt":"message","storage":"demo:state"}
```

前提是队伍 `example` 已存在。与旧版在解析阶段拒绝不同，新版会把该组件放入队伍状态，随后同步队伍数据或保存记分板时，序列化会抛出 `IllegalArgumentException`。对于保留了这一状态、仍正常启用自动保存的服务器，自动保存会沿未捕获的异常退出服务器主循环。把 storage 组件直接用作记分板显示名称也有同样的序列化缺口。

## 只检查坐标和维度的谓词不再要求目标位置已加载

位置条件用于进度和数据包谓词，也会被 `/execute if predicate` 的 `location_check` 使用。新版将加载检查移到需要读取世界数据的具体条件中。

### 差异出现的场景

目标区块未加载，位置谓词只限制坐标、维度，或没有任何具体限制。例如把命令执行位置移到未加载区块，再检查一个只限制主世界维度的 `location_check`。

### 版本变化

- 19w38b：整个位置条件直接失败，即使坐标和维度均满足要求，甚至没有任何具体限制。
- 19w39a：上述条件可以正常匹配；需要读取生物群系、结构、亮度、方块或流体时，仍要求目标位置已加载。

显式写出的空对象与省略字段不同：`block:{}`、`fluid:{}`、`light:{}` 都会建立需要已加载位置的条件；省略这些字段才是不读取对应世界数据的无限制条件。数据包若利用旧版失败行为把普通位置条件兼作区块加载检查，结果会改变。

## 命令文本解析遇到栈溢出时返回语法错误

命令读取 JSON 文本参数时，需要递归解析文本结构。新版为这个入口增加栈溢出处理。

### 差异出现的场景

`/tellraw` 等命令的 JSON 文本嵌套深到使解析耗尽调用栈。

### 版本变化

- 19w38b：`StackOverflowError` 逃出文本解析入口，不能由这一入口转换为命令语法错误。

## 隐身生物可能失去本体的发光轮廓

新版将发光轮廓的绘制由单独渲染实体，改为复制正常绘制提交的模型。隐身生物的本体若没有进入正常绘制，也就无法产生对应轮廓。

- 19w39a：隐身本体没有进入正常绘制时，也不会产生本体轮廓，上述苦力怕会失去旧版的身体轮廓。

装备等仍然可见的附加部分可能保留轮廓。旁观者，以及允许看见隐身队友的同队玩家，不属于本体被完全省略的条件。
