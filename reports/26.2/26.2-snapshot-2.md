# Minecraft 26.2 Snapshot 2 变更分析

- 上一个版本：`26.2-snapshot-1`
- 当前版本：`26.2-snapshot-2`

## 比较器已经被移除后，不再继续掉落物品或恢复方块

新版在处理比较器的邻居更新，以及玩家切换比较器模式后的输出刷新前，重新确认原位置仍然存在比较器。这会改变利用连锁更新制造额外掉落物或恢复比较器的装置。

### 差异出现的场景

容器等方块的变化已经产生了比较器更新，但比较器在该更新执行前，因同一轮连锁更新失去支撑并被移除；或者玩家切换比较器模式时，设置新模式引发的方块更新先移除了比较器。

### 版本变化

- Snapshot 1：仍然按照此前保存的比较器状态继续处理。若下方没有支撑，可以再次生成比较器掉落物；若原位置已换成其他方块，还可能移除该位置当前的方块。切换模式后的输出刷新则可能在需要改变通电状态时，把已经移除的比较器再次写回世界。
- Snapshot 2：如果原位置已经不再是比较器，就跳过这些后续处理，避免上述额外掉落、错误移除或恢复方块。

邻居更新的保护位于中继器与比较器共用的实现中。判断针对的是方块类型；原位置仍然是同类型方块时，会继续处理。

## 海豚换气优先寻找正上方，不再搜索斜对角的空气柱

海豚剩余空气低于 140 刻时，会寻找空气或可供换气的气泡柱。新版修改了目标的搜索范围与顺序，也保留了开始换气时首次计算出的路径。

### 差异出现的场景

海豚被养在带有多个换气口的水池，或者只有角落、侧面设有空气空隙和气泡柱。搜索的高度范围为海豚所在方块高度到上方 8 格，包含两端。

### 版本变化

- Snapshot 1：搜索周围 3×3 的全部 9 根方块柱，按照先 X、再 Y、最后 Z 的顺序取第一个符合条件的位置。因此，即使正上方存在换气口，也可能先选到北侧或斜对角的空隙。刚开始换气时，首次设置的导航路径随即被停止，要等换气目标后续执行时重新寻找。
- Snapshot 2：先从下到上搜索海豚所在的整根方块柱，找不到才依次搜索北、东、南、西四根相邻柱；四个斜对角不再参与搜索。开始换气时先停止旧路径，再寻找换气位置，新建立的路径会被保留。

如果只有斜对角存在可供换气的位置，新版不会直接把该位置选作本次换气目标；没有找到目标时，会尝试前往自身上方的位置。水池内海豚选择的上浮路线因此会变化。

## 水生生物需要更接近路径终点的高度

鱼、蝌蚪、守卫者、海豚和鹦鹉螺等使用水中导航的生物，在水下沿路径移动时，新版把“已经接近当前路径点”的竖直距离要求从小于 1 格收紧到小于 0.5 格。

例如，生物已经在路径终点的水平位置附近，但身体底部仍比目标高度低 0.75 格：Snapshot 1 可以把该路径判为完成；Snapshot 2 会继续向目标移动，直到高度差小于半格。它会改变生物到达喂食、跟随或游动目标时停下的位置，尤其影响水池内带有高度变化的路线。

这个限制针对接近路径点的判定。路径还有后续节点且满足直达、转角等跳过节点条件时，生物仍可以继续前进，因此并非所有中间节点都必须逐一精确经过。

## 很老的存档并行迁移结构数据，部分失败可能漏报

仍保留 `Monument.dat`、`Temple.dat`、`Fortress.dat` 等旧式结构文件的存档，在升级时需要把结构起点和引用迁入区块。新版把这一阶段从逐个等待区块转换完成，改为同时处理多个区块，并把转换工作移至后台线程执行。

### 差异出现的场景

直接升级仍需迁移旧式结构文件的存档。已经完成这次结构数据迁移的存档不受该步骤影响。

### 版本变化

- Snapshot 1：每处理一个区块，都等待它的读取、转换与写入结束，再继续下一个区块。任意一个区块的这些操作以异常结束，都会通过等待操作向外报告，阻止该轮升级正常完成。
- Snapshot 2：多个区块的转换可以并行进行，阶段结束时等待剩余任务。正常情况下迁移的数据内容相同；但中途回收已完成任务时，只等待“任意一个任务”的结果，然后把所有已结束的任务一起移出等待列表。

后一种处理产生一个异常分支：如果同一批任务中，一个成功任务先被选中，同时另一个任务已经失败，新版可能把失败任务一并移出列表，并计入完成数，没有向升级流程报告失败。相关区块的结构数据因此可能未迁入，升级却继续进行。后续步骤还会删除旧式结构文件；缺失结构识别数据可能影响海底神殿、沼泽小屋、下界要塞等区域使用专属生物生成规则。

## Vulkan 下重载资源包会重新编译着色器，但编译失败可能导致客户端崩溃

新版在重载资源时清空 Vulkan 的着色器缓存，使资源包对已有着色器的修改可以生效；同一清理逻辑也引入了处理编译失败结果的错误。

### 差异出现的场景

客户端使用 Vulkan，按 F3+T 重载资源，或切换修改了现有核心着色器的资源包。

### 版本变化

- Snapshot 1：重载只清理渲染管线，保留已编译的着色器。同一着色器标识、类型与编译参数对应的缓存会继续复用，修改源码后可能仍显示旧效果，需要重新启动才能重新编译。
- Snapshot 2：同时释放并移除着色器缓存，重载后根据当前资源包重新编译，正常的着色器修改可以在本次重载中生效。

### 实际影响

如果资源包造成着色器源码缺失或编译失败，Vulkan 会把失败结果缓存为一个共用的“无效着色器”。新版清理时也会释放这个对象，但它保存的是普通 Java 堆缓冲区，并非可释放的原生内存。此时会发生无效的原生内存释放，可能直接使客户端进程崩溃。

这既可能出现在首次加载错误资源包的失败清理阶段，也可能出现在之后的缓存清理中。Snapshot 1 没有这次无效释放：首次编译失败可以进入资源加载失败处理；如果该着色器此前已有有效缓存，则还可能继续沿用旧着色器。

## 选择 OpenGL 也需要先加载 Vulkan 相关原生库

在能够正常使用 OpenGL，但 Vulkan 加载器或 shaderc、spvc、vma 原生库缺失、损坏或无法加载的环境中，客户端启动结果发生变化。

- Snapshot 1：启动初期不主动加载这些库。选择优先使用 OpenGL 且 OpenGL 创建成功时，可以避开 Vulkan 后端的库加载；默认启动时，如果 GLFW 判断不支持 Vulkan，也可以回退到 OpenGL。
- Snapshot 2：在读取图形后端设置、创建窗口前，就主动加载这些 Vulkan 相关库。任何一次加载失败都会进入原生库加载崩溃处理，启动不会继续到 OpenGL 回退阶段。即使使用新的 `--graphicsBackend opengl` 参数，也不会绕过这一检查。

这里的条件是原生库无法加载。仅仅显卡不满足 Vulkan 渲染要求，仍由后端选择流程决定是否回退。

## Vulkan 无法用于当前显示环境时，能够继续选择其他后端

以下修复发生在原生库已经成功加载之后，影响图形后端创建失败时是否还有机会启动游戏。

- GLFW 无法提供所需的 Vulkan 窗口表面扩展时，Snapshot 1 抛出普通运行时异常，直接中断初始化；Snapshot 2 把它作为可处理的后端创建失败，继续尝试 OpenGL。
- 枚举到的某个 Vulkan 设备没有满足游戏要求的图形、计算及显示队列时，Snapshot 1 在设备适用性检查中可能直接触发空指针异常，连带中断其他显卡的选择；Snapshot 2 将该设备判为不适用，继续寻找其他设备，全部不适用时再进入正常失败和回退流程。

## 图形后端新增启动参数，Vulkan 正确采用非独占全屏设置

- 新增客户端启动参数 `--graphicsBackend opengl`、`--graphicsBackend vulkan` 和 `--graphicsBackend default`，本次启动会以该参数覆盖游戏内保存的图形 API 选择。它控制尝试顺序：`opengl` 先尝试 OpenGL，`vulkan` 和 `default` 先尝试 Vulkan；首选后端创建失败时，仍会尝试另一后端。Snapshot 1 没有这个覆盖入口。
- 关闭“独占全屏”并使用 Vulkan 时，Snapshot 1 在创建窗口前重置了窗口选项，丢失非独占全屏设置；Snapshot 2 在每次尝试图形后端前重新设置该选项，并取消 Vulkan 内部的重复重置，使 Vulkan 及失败后回退的窗口都采用玩家保存的设置。

## Vulkan 下的“极佳！”画质不再因为 AMD 名称而改用 RGSS

显卡名称含有 `AMD`，且使用 Vulkan 后端时，应用“极佳！”画质预设的纹理过滤结果发生变化：Snapshot 1 会选择 RGSS；Snapshot 2 会选择各向异性过滤，使倾斜表面的纹理过滤效果随之变化。

这是因为旧版按显卡名称对所有后端统一判断，新版仅在 OpenGL 后端保留这项已知问题的规避。该变化发生在应用画质预设时；单独手动选择纹理过滤的操作仍由相应设置控制。

## 关闭客户端后，遥测线程不再阻止进程退出

只要客户端曾启动遥测发送线程，Snapshot 1 的该线程即使空闲等待，也会作为非守护线程阻止 Java 进程自然退出。因此，游戏窗口和其他工作已经关闭后，进程仍可能继续存在。

Snapshot 2 将遥测发送线程改为守护线程。如果退出时只剩此类后台线程，进程可以正常结束；尚未完成的遥测发送也不再使客户端继续存活。

## 图形错误处理与调试信息调整

- GLFW 在非渲染线程回报错误时，Snapshot 1 的错误回调会因线程断言再抛出异常；Snapshot 2 会记录线程错误并继续记录原来的 GLFW 错误，使这次回调不再因为线程检查而中断。
- F3 的帧率信息由只显示是否开启垂直同步，改为显示实际呈现模式：`immediate`、`mailbox`、`fifo` 或 `fifo relaxed`。原有的垂直同步开关及后端选择模式的优先次序保持相同。
