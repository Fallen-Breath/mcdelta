# Minecraft 1.16.5-rc1-1 变更分析

- 上一个版本：1.16.4
- 当前版本：1.16.5-rc1-1

## 朝下发射器在黑曜石旁尝试点火时不再使世界崩溃

发射器使用打火石时，如果普通火无法留在目标位置，还会检查该位置是否处于可激活的下界传送门框架内。新版修复了这项检查处理竖直方向时抛出异常的问题。

### 差异出现的场景

在主世界或下界，让装有打火石的发射器朝下，对着空气发射；目标空气的六个相邻位置中至少有一块黑曜石，但下方没有可支撑火的完整顶面，周围也没有让普通火能够附着的可燃方块；相邻黑曜石没有构成可激活的完整传送门框架。例如，将朝下发射器的前方空气紧邻一面黑曜石墙，并让这格空气的下方悬空。

### 版本变化

- 1.16.4：传送门检查试图把朝下方向水平旋转，抛出 `IllegalStateException`。异常沿发射器的计划刻上抛，导致运行该世界的服务器崩溃；单人游戏中的内置服务器也受影响。
- 1.16.5-rc1-1：遇到竖直方向时，改为随机选取一个水平轴，检查传送门框架。在上述不完整框架中，检查失败，发射器正常发出失败反馈，打火石不损失耐久，世界继续运行。

正常放置的朝上发射器，其自身顶面通常已足以支撑前方的火，不会走到上述传送门检查。玩家手持打火石或火焰弹时，传入的也是玩家的水平方向，因此这一修复主要影响发射器的上述异常场景。

## 同一位置的地点记录发生类型冲突时继续登记

工作站、床、钟和下界传送门等位置会登记为 POI，供村民和其他系统查询。新版改变了同一坐标重复登记为不同类型时的处理方式。

### 差异出现的场景

世界中已有某坐标的地点记录，又在未清除旧记录的情况下，为该坐标登记另一种地点类型。冲突可以出现在异常的地点数据加载或后续登记过程中。正常更换工作站会先删除旧类型、再加入新类型，只有记录已不一致等情况才进入本次修改的分支。

### 版本变化

- 1.16.4：抛出 `POI data mismatch: already registered at ...` 异常，新的登记无法完成；如果异常发生在世界更新等未吞掉该异常的调用中，可以使世界运行中断。
- 1.16.5-rc1-1：通常运行环境中记录同样内容的错误日志，然后以新类型覆盖该坐标的主记录，继续执行后续登记和保存。仅开发环境仍抛出异常。

### 实际影响

冲突不再直接打断登记，但覆盖后的记录会使用新类型的初始可认领数量，旧记录的占用状态不会转移过去。

这次覆盖仍会把旧类型留在内存中的分类查询集合里。因此，冲突发生后，按类型搜索工作站等地点的结果仍可能包含该位置的旧类型，而按坐标核对时已经读到新类型；附近村民寻找地点与核对地点时可能得到不一致的结果。保存该区段并重新加载后，持久化数据只包含覆盖后的主记录，不会再从这次冲突恢复出旧类型记录。

## 与 1.16.4 的原版联机不再兼容

原版服务器在登录握手时要求客户端与服务器的协议号完全一致。本次协议号从 754 改为预发布协议号 1073741834，因而改变了与 1.16.4 的直接联机兼容性。

### 差异出现的场景

原版客户端与原版服务器直接联机，其中一端固定使用 1.16.4，另一端分别使用 1.16.4 和 1.16.5-rc1-1。服务器正常开放连接，且没有协议转换层。

### 版本变化

- 1.16.4：客户端和服务器均使用协议号 754，双方的版本检查可以通过。
- 1.16.5-rc1-1：升级的一端改用协议号 1073741834，与固定使用 1.16.4 的另一端不一致，服务器会在登录握手阶段断开连接。这对客户端升级和服务器升级两个方向都适用；两端都升级到本版本后，版本检查才可通过。

服务器列表的状态查询不要求协议号相同，因此跨这两个版本仍可查询服务器状态。

## 屏蔽名单服务失败时，聊天和社交屏幕可能反复卡顿

客户端通过在线社交服务读取账号屏蔽名单，再据此过滤聊天并显示玩家的屏蔽状态。按两端构建文件声明的依赖运行时，认证库从 authlib 2.1.28 回退到 2.0.27，失败请求的重试方式随之改变。

### 差异出现的场景

客户端启动时已成功创建在线社交服务，账号允许聊天，但屏蔽名单尚未成功缓存；此后屏蔽名单请求超时、失败或返回空结果。接收需要进行屏蔽检查的聊天消息，或打开社交屏幕查看其他玩家，会触发这项查询。启动时认证检查就失败、已经退回离线社交服务的情况不适用。

### 版本变化

- 1.16.4：一次请求后设有 120 秒冷却，期间再次检查玩家时直接按未屏蔽处理，避免连续发送失败请求。没有具体发送者的消息使用全零 UUID，也直接跳过在线屏蔽查询。
- 1.16.5-rc1-1：失败后没有重试冷却，下一次检查可以立即再次同步请求；全零 UUID 也会进入名单查询。若服务持续缓慢或不可达，接收聊天、绘制社交屏幕时可能反复等待网络返回，造成客户端卡顿。

两版成功取得名单后都会缓存它。因此，差异集中在尚未获取名单和请求失败的阶段；新版也可能在服务恢复后更早取得名单。

## 部分受屏蔽服务器域名可以通过 SRV 记录继续连接

客户端可以通过域名的 SRV 记录取得服务器的实际主机和端口。按两端构建文件声明的依赖运行时，patchy 从 1.3.9 回退到 1.1，不再安装旧版提供的 DNS 屏蔽检查，改变了部分受屏蔽域名的连接结果。

### 差异出现的场景

使用默认端口 25565 连接一个受屏蔽的服务器域名，该域名的 SRV 记录指向另一个未受屏蔽的主机，其 IP 也未受屏蔽。对照中的 1.16.4 客户端已通过启动日志配置加载 `LegacyXMLLayout`，由此安装了 patchy 1.3.9 的 DNS 屏蔽检查；没有加载该组件的启动环境不适用。

### 版本变化

- 1.16.4：DNS 屏蔽检查阻止对原域名的 SRV 查询。客户端随后尝试连接原域名，仍会被连接目标检查拦截。
- 1.16.5-rc1-1：patchy 1.1 不安装这层 DNS 检查，客户端可以读到 SRV 记录，转而尝试连接记录指向的主机和端口；在上述目标主机及 IP 均未受屏蔽的条件下，可以通过屏蔽检查。

两版游戏源码的 SRV 解析规则相同，最终连接目标的屏蔽检查也都保留。差异来自读取 SRV 记录前是否拦截原域名，不代表 SRV 记录指向的任意目标都能通过检查。

## 旧单人世界的升级备份与版本确认

- 从世界列表打开最后由 1.16.4 保存的同一个世界时，1.16.4 可以直接进入；1.16.5-rc1-1 的世界数据版本从 2584 升为 2585，会先显示升级备份确认，玩家可以选择备份后进入或直接继续。
- 用 1.16.5-rc1-1 保存该世界后，再从 1.16.4 的世界列表打开，旧版会将其识别为较新版本保存的世界，并显示版本确认；继续在 1.16.5-rc1-1 中打开则没有这一版本差异确认。
