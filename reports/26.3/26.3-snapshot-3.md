# Minecraft 26.3-snapshot-3 变更分析

- 上一个版本：`26.3-snapshot-2`
- 当前版本：`26.3-snapshot-3`

## 铜门刮锈和除蜡不再被另一半门还原

对铜门任一半使用斧进行刮锈或除蜡时，Snapshot 2 会先根据邻接方块修正变换后的门。由于另一半仍是原来的铜门，这次修正会把目标状态重新改回原来的门，导致操作消耗耐久却没有完成变换。Snapshot 3 在这两种门的变换中跳过这次预先修正，先改变点击的半扇门，再由门的联动更新改变另一半，刮锈和除蜡可以正常完成。

## 挖掘疲劳 III 的挖掘速度提高到原来的十倍

Snapshot 2 对挖掘疲劳 I、II、III、IV 及以上分别使用 `0.3`、`0.09`、`0.0027`、`0.00081` 的挖掘速度倍率。Snapshot 3 改为每升一级再乘 `0.3`，因此 III 为 `0.027`，IV 为 `0.0081`，两者都是旧版的十倍；V 为 `0.00243`，VI 为 `0.000729`，更高等级继续递减。

远古守卫者施加的挖掘疲劳 III 因而不再像旧版那样大幅压低挖掘速度。以上比较针对挖掘进度；具体破坏方块所需刻数仍受工具、方块硬度和其他挖掘条件影响。

## 静止实体不再因一个重力步长反复弹起

实体向下碰撞可反弹的地面时，如果本次向下速度恰好等于该实体的有效重力，Snapshot 2 仍允许计算反弹；Snapshot 3 将这一等值情形归入不反弹。已经落稳、仅因重力产生这一小步向下运动的实体，可以保持停稳；依赖这种微小反弹持续触发的装置和振动检测会失去对应事件。较大下落速度的反弹仍按原有条件处理。

## 酿造台使用配方数据，并改变玻璃瓶与特殊药水的处理

酿造规则从固定的药水转换列表改为 `minecraft:brewing` 配方。原版常规药水的酿造路线保留，但既有酿造台与自动供料会遇到以下差异。

- Snapshot 2 允许玩家和漏斗把玻璃瓶放入下方三个槽位；Snapshot 3 只允许放入酿造配方中出现的输入物品。默认配方没有玻璃瓶，因此这些槽位不再接收玻璃瓶。
- Snapshot 2 可以用火药把幸运药水转换为喷溅型，再用龙息转换为滞留型。Snapshot 3 的默认容器转换配方只为酿造路线中出现的药水生成，未包含幸运药水；幸运药水仍可放入药水槽，但这两步转换不再发生。数据包增加的药水类型也需要各自的容器转换配方。只有自定义效果、没有基础药水类型的药水，旧版会为这两类容器转换消耗材料但保持瓶子原样，新版没有匹配配方时不会启动。
- 酿造消耗材料槽中的最后一瓶龙息时，Snapshot 2 先扣除材料，再读取其容器返还物，空堆叠被当作空气而漏掉玻璃瓶；Snapshot 3 先读取返还物，再扣除材料，最后一瓶龙息也会留下玻璃瓶。

数据包现在可以修改、移除或添加酿造配方，改变酿造台的输入、材料和产物。槽位是否接受某类物品取决于物品有没有出现在配方中，实际能否酿造还会检查对应药水内容。

## 队伍的友军伤害规则扩展到接触伤害和爆炸

同一队伍关闭友军伤害时，Snapshot 3 增加了以下保护；Snapshot 2 的这些伤害路径没有进行这一检查。

- 河豚不再通过接触伤害同队生物或玩家，也不会由这次刺伤附加中毒。
- 史莱姆和岩浆怪不再通过接触攻击伤害同队玩家、铁傀儡。
- 末影龙的接触攻击和翅膀攻击不再伤害同队生物；翅膀的推开运动仍会发生。
- 爆炸直接来源实体与受击实体同队时，不再造成该次爆炸伤害。爆炸的击退和方块破坏仍按各自规则处理。此处检查的是爆炸实体本身的队伍，例如爬行者或已点燃的 TNT，而不是自动改查其点燃者。

此外，`Team` 实体数据以前只由生物读取，现在由所有实体读取。可以在召唤或载入 TNT、掉落物等非生物实体时，直接通过 `Team` 加入已有队伍。

## 溺尸恢复远距离近战追击，并能向近处不可达目标投掷三叉戟

Snapshot 2 以距离是否达到 3 格作为溺尸近战与远程攻击目标的分界。没有三叉戟的溺尸在目标距离达到 3 格时也会停用近战追击，远程攻击又要求持有三叉戟。Snapshot 3 仅在确实应当投掷三叉戟时停用近战，因此无三叉戟的溺尸可以持续追近远处目标。

持有三叉戟时，距离达到 3 格仍可启用远程攻击；新版还允许在不足 3 格、超出近战攻击范围、且通向目标所在方块的路径无法到达时启用远程攻击。把目标放在近处但让溺尸无法走到的诱导布局，可能由原先近战追击改为投掷。

## 正常启动恢复服务公钥、其他玩家外观与聊天签名验证

Snapshot 2 在普通启动时把“是否启用服务公钥”的开关关掉，取得空的官方服务公钥集；Snapshot 3 反转了这一传参，使普通启动启用服务公钥，离线开发模式才关闭。

在官方服务公钥能正常获取、玩家资料签名有效的情况下，新版可以验证其他玩家的皮肤、披风和鞘翅外观并显示它们。旧版缺少公钥时，带签名的外观数据会被视为签名无效，而其他玩家外观的查询要求有效签名，因而退回默认外观。客户端还可以正常建立经过公钥验证的聊天会话；旧版会忽略这些会话并退回不验证签名的路径，收到的聊天签名会被去除。

离线开发模式同时禁用了好友入口、好友开关和好友功能标记；普通联网模式的好友入口继续可用。

## 服务器接入新连接时避免与旧连接关闭互相等待

Snapshot 2 在网络线程接入连接时，直接获取连接列表的锁；服务器主线程遍历并更新已有连接时也持有这把锁。如果同一个网络线程正在等待加入新连接，而主线程此时因为登录超时等原因同步关闭该网络线程上的旧连接，两边可能互相等待，使服务器停止推进。

Snapshot 3 先将新连接放入无需取得这把列表锁的待接入队列，再由主线程在连接刻开始时转入活动列表。上述接入与关闭并发的情况下，网络线程可以继续完成旧连接的关闭，避免这一锁等待链造成全服停滞。

## 高度边界附近的范围扫描可能抛出数组越界异常

多种邻近方块检测改为直接按区块段扫描。新版扫描没有裁剪超出世界建筑高度的纵向范围，而是直接用该高度计算区块段数组下标。

### 差异出现的场景

扫描范围跨出维度的最小或最大建筑高度，且扫描没有在到达越界区块段前提前返回。例如主世界 `y=319` 的无水耕地执行湿润检测，会扫描到 `y=320`；在 `y=-64` 的下界岩上使用骨粉，会向下检查到 `y=-65`。

### 版本变化

- Snapshot 2：逐方块读取范围，建筑高度外的位置被当作空气处理，可以正常得到检测结果。
- Snapshot 3：上述区块段下标分别为数组长度之外或负数，抛出数组越界异常。无水耕地的随机刻等服务器刻路径会因此失败，并可能使服务器崩溃；骨粉的目标检查也可能首先使客户端崩溃。

同一缺少边界裁剪的扫描还用于蘑菇、藤蔓、眼眸花、蜂巢、树苗的附近方块检测，以及部分实体空间检查。异常取决于实际扫描范围和是否提前找到结果。

## 液体检查会计入碰撞箱整数边界另一侧的方块

Snapshot 2 检查碰撞箱内是否有液体时，不包含最大 X、Y、Z 边界之外的方块。Snapshot 3 改用的范围扫描包含最大坐标所在的整格；当最大边界恰好是整数时，与该面紧贴、位于碰撞箱之外的那一格也会被扫描。

因此，在这类精确边界上，如果外侧紧贴的是水或熔岩，新版会判为接触液体。使用这项检查的生物生成空间判断、随机传送落点检查和实体自由移动空间检查，可能拒绝旧版允许的位置。

## 矿石生成恢复对不同高度石质方块的替换

Snapshot 2 将普通矿石的整个替换条件限制在 `y≥0`，将深层矿石的整个替换条件限制在 `y≤8`。这使负高度的石头、花岗岩、闪长岩、安山岩无法被对应普通矿石矿团替换，也使高于 8 的深板岩无法被对应深层矿石替换。

这改变新生成区块中的矿石替换结果，以及手动放置对应地物的结果；已生成的矿石不会被重新转换。

## 新生成海带更短，浅水与底部检查也有变化

海带生成从专用逻辑改为方块柱地物，影响新海域和手动放置海带地物。

### 版本变化

- Snapshot 2：空间充足时，生成高度为 2～11 格；水深不足时可缩短，并在顶部保留至少一格水。每层放置前检查海带能否在当前位置存活。
- Snapshot 3：空间充足时，生成高度为 1～10 格。方块柱的前探检查还要求最顶层之上保留两格水，因此只有两格深的水域不再生成海带，受水面限制的海带顶端也会更低。

## Straw Bed 提供不改变重生点的一次性睡眠

Snapshot 2 只能使用原有床来进行常规睡眠。Snapshot 3 新增的 Straw Bed 在主世界满足睡眠条件时可以睡觉、计入跳过夜晚的人数并重置距上次休息时间，但不设置重生点；离床时自行消失，不掉落床。它在下界和末地使用时直接消失，不产生普通床的爆炸。三块干草块可以合成四张。

## 带方块变换能力的方块物品可以在放置失败后继续变换

给方块物品添加 `minecraft:block_transformer` 时，Snapshot 2 的右键处理只尝试放置方块，失败后仅考虑是否可食用，不调用该变换组件。Snapshot 3 在放置未消耗操作后先尝试组件变换，再处理可食用行为。自定义方块物品因此可以在不能放置的条件下执行耕地、去皮或数据包定义的其他方块变换；可以正常放置时仍先放置。

## 生物移动同步保留反弹路径，并调整客户端预测的衔接

## 错误的配方、进度和战利品数据会使整次加载失败

数据包中的配方、进度、战利品表、物品修饰器、谓词或槽位来源出现 JSON 解析或数据解码错误时，Snapshot 2 通常记录错误并跳过该文件，继续加载其他有效内容。Snapshot 3 将这些资源一起纳入注册表加载，收集到解码错误后会令整次加载失败。

## 命令不再把重复设置算作成功

- `/gamerule` 把规则设为已有值时，Snapshot 2 仍成功；Snapshot 3 报告没有改变。依赖条件命令方块或 `execute store success` 判断这类命令的装置会得到失败结果。
- `/time` 重复设置同一个绝对刻数、已经到达的时间标记、已有的暂停/运行状态或已有速度时，新版同样失败；旧版继续执行并报告成功。
- `/fillbiome` 的计数由所有匹配的生物群系采样单元改为真正改变的单元。区域本来已是目标群系时，旧版仍报告成功和匹配数量，新版失败；只改变部分区域时，返回值也会减少。
- `/schedule clear` 由自由文本改用资源标识符：清除默认命名空间函数时，新版允许省略 `minecraft:` 并补全它；旧版按输入字符串原样查找。函数标签的任务名称含有 `#`，新版参数不接受这一字符，因此不能再用原来的 `#namespace:tag` 名称清除标签任务。等待队列含有标签任务时，清除参数的补全还会尝试把带 `#` 的任务名解析为标识符，从而抛出异常，不能正常完成补全。

## 资源包模型的方向明暗设置与透明深度改变

模型元素原先的 `shade` 布尔值由 `shade_direction_override` 方向字段替代。原版使用 `shade:false` 的模型改为指定 `up` 以维持原来的顶面明暗。自定义资源包继续只写 `shade:false` 时，新版会忽略旧字段并按模型面的实际方向着色，侧面可能变暗；新字段可指定六个方向之一的明暗。

启用改进的透明渲染时，新版还将最近透明表面的深度写回主深度缓冲。读取主深度的后处理因此可以看到玻璃、水面等透明表面的深度，而旧版在这一合成阶段不会写入这些深度。
