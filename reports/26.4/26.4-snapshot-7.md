- 上一个版本：`26.4-snapshot-6`

## 铜傀儡搬运时重新读取大箱子的有效库存

铜傀儡选中箱子后，需要走近并在默认刻速下进行约 3 秒的交互。本次改变了这段时间内箱子组合或可打开状态发生变化时，实际访问的库存。

### 差异出现的场景

铜傀儡已经选中一个大箱子的其中一半；玩家随后拆除、替换另一半，或在另一半上方放置阻挡箱子打开的方块。选中的那一半仍保留原来的方块实体。

### 版本变化

- Snapshot 6：铜傀儡保存选定目标时取得的库存对象，之后开关箱盖、判断取放及完成搬运都使用该对象。另一半拆除或替换后，仍可能访问原先组合中的旧箱子库存；另一半后来被堵住，也不会通过重新组合箱子发现这一变化。
- Snapshot 7：开始交互、交互动画及真正取放时重新取得箱子库存。另一半消失时，只访问仍存在的半边；另一半被替换时，访问现存组合；组合箱子被挡住而无法取得库存时，停止当前目标的交互。

## 涂蜡铜傀儡被雷击后保留氧化程度与涂蜡状态

涂蜡用于停止铜傀儡继续氧化，新版让雷击除锈也遵循这一限制。

### 差异出现的场景

一个已有氧化程度、并已涂蜡的铜傀儡受到雷击。

### 版本变化

- Snapshot 6：雷击仍使它降低一级氧化程度，并使涂蜡个体恢复自然氧化。
- Snapshot 7：涂蜡铜傀儡不执行雷击除锈，保留原来的氧化程度及涂蜡状态。

未氧化的铜傀儡本来就不会进入这段除锈处理；本次差异针对已氧化且涂蜡的个体。

## 着火阻止冻结，皮革装备阻止细雪中的变种转化

冻结积累、冻结伤害与细雪中的生物转化使用不同的检查。本次分别为它们增加了新的限制。

### 差异出现的场景

一是能够冻结的实体正在着火，同时受到冻结来源影响，尤其是已有冰冻效果。二是骷髅或能够经细雪转化的僵尸穿着任意一件防冻装备，仍停留在细雪中。

### 版本变化

- Snapshot 6：着火本身不阻止冻结检查。骷髅和僵尸的细雪转化只检查是否处于细雪中，即使穿着防冻装备，也会继续累计转化时间。
- Snapshot 7：着火期间不能积累冻结，生物已有冻结时间会按每游戏刻 2 刻消退，期间也不承受冻结伤害。骷髅和僵尸穿着防冻装备时，不再累计细雪转化时间；已经开始的转化也会取消，移除装备后需要重新积累。

原版防冻装备标签包括皮革头盔、皮革外套、皮革裤子、皮革靴子和皮革马铠；这里检查的是生物的护甲装备槽。普通骷髅的目标变种为流浪者，普通僵尸的目标变种为冻尸。着火检查加入的是一般冻结机制，细雪转化新增的条件是防冻装备检查。

## 多种远程攻击不再在射击时检查固定距离上限

雪傀儡、女巫、羊驼、凋灵和持三叉戟的溺尸等生物共用一套远程攻击行为。本次移除了其中“冷却结束时，目标距离必须在攻击半径内”的条件。

### 差异出现的场景

生物已经保有有效攻击目标，远程攻击行为仍在运行，并且冷却恰好结束。此时目标在视线内，但已经退到该远程攻击行为设定的半径外。例如雪傀儡的该半径是 10 格，羊驼的是 20 格。

### 版本变化

- Snapshot 6：目标超出半径时，本次攻击直接跳过，生物继续尝试接近目标。
- Snapshot 7：只要仍有视线，本次攻击可以发出；距离半径仍用于决定何时停止靠近、计算攻击间隔及攻击参数，但不再直接拒绝这次发射。

### 实际影响

把已经激怒的生物与目标隔开到该半径外，不再能单凭这段距离阻止其发射。该变化没有取消目标选择、视线和各生物自身攻击方法的限制；目标已经丢失或被遮挡时，不能据此继续远程攻击。

## 停播后补放上方箱子可重新启动唱片轮播

唱片机上方放置符合轮播条件的单箱后，可以交换唱片并连续播放。本次补上了“机内有唱片，但已停止播放”时的自动启动。

### 差异出现的场景

唱片机保留了一张已播完的唱片、当前没有播放；玩家随后在它正上方放置符合轮播条件的箱子。机内物品必须带有可供唱片机播放的数据组件。

### 版本变化

- Snapshot 6：有唱片时只推进既有播放计时；已经停播的唱片机不会因为此时具备箱子轮播条件而自行开始。
- Snapshot 7：在后续方块实体刻检测到停播且满足轮播条件，就尝试切换到上方箱子中的下一张唱片；没有其他唱片时，重新播放机内唱片。

新版的“下一首”提示也可以在尚未建立播放列表位置时，预告箱子中的第一张可播放唱片。

## 蒸发维度中冰融化也会产生方块破坏振动

幽匿感测体通过游戏事件接收振动，本次将冰在水会蒸发的环境中消失的过程，也纳入方块破坏事件。

### 差异出现的场景

普通冰因方块光照随机刻而融化，或霜冰达到融化条件，所在位置的环境属性会使水蒸发，例如下界。附近有能够接收该事件、且没有被羊毛阻隔的幽匿感测体或其他振动接收者。

### 版本变化

- Snapshot 6：会留下水的融冰产生方块破坏游戏事件；水会蒸发时，直接移除冰而不发出这个事件。
- Snapshot 7：先发出方块破坏事件，再决定融成水或直接移除。因此，水会蒸发的位置也能由融冰触发振动。

事件对应的振动频率为 12；校频幽匿感测体可以按这一频率检测。修改针对融化处理，玩家直接挖冰走的是另一条破坏流程。

## 物品展示框与荧光物品展示框放置时检查世界边界

画和物品展示框共用悬挂实体放置流程，本次把画原有的边界限制也用于展示框。

### 差异出现的场景

在世界边界附近放置物品展示框或荧光物品展示框，其放置检查所使用的占用范围有一部分越过边界，其余依附和碰撞条件均满足。

### 版本变化

- Snapshot 6：这两种展示框只按自身能否依附、是否与方块及其他悬挂实体冲突来判定，可以接受上述位置。
- Snapshot 7：悬挂实体统一增加世界边界碰撞检查，拒绝上述放置。画原先已经单独进行同样检查，因此画的正常放置结果不变。

此条件在放置入口检查；本次没有让已有展示框因后来收缩世界边界而按此条件自动掉落。

## 异常烹饪总时长不再在冷却进度时使世界崩溃

熔炉、烟熏炉、高炉和熄灭的营火，会在停止烹饪时逐渐回退已有进度。本次修正了总时长为负数时的处理。

### 差异出现的场景

通过命令或存档编辑，使熔炉类方块的 `cooking_time_spent` 为正数、`cooking_total_time` 为负数，方块未在燃烧且燃料槽或原料槽为空，因而进入进度回退分支；或使熄灭营火某槽位的 `CookingTimes` 为正数、对应 `CookingTotalTimes` 为负数。

### 版本变化

- Snapshot 6：把进度限制到“0 至负数”的区间，触发非法上下界异常；方块实体刻异常会导致服务器或单人世界退出。
- Snapshot 7：先将回退进度所用的上限与 0 取较大值，上述异常数据会将回退进度归零，世界继续运行。

普通配方产生的非负烹饪时长仍按原来的方式回退。

## 经验球停止追踪已离开的玩家

经验球会持续追逐选中的附近玩家，新版把玩家实体被移除也作为重新选择的条件。

## 下落距离保留每刻位移的小数精度

摔落伤害取决于累计的下落距离，本次提高了把实际位移计入这段距离时的精度。

### 差异出现的场景

实体连续下落，累计距离恰好靠近摔落伤害的取整边界；尤其是使用精确坐标、特殊位移或自定义属性控制落差的装置。

### 版本变化

- Snapshot 6：累计每一刻向下位移前，先把它转换为单精度浮点数，再加入下落距离。
- Snapshot 7：直接使用原来的双精度位移累计，减少逐刻舍入误差。

摔落伤害仍由累计距离、可安全下落距离及伤害倍率计算并向下取整，计算中仍有原来的 `0.000001` 容差。大多数正常落差没有区别；在加上容差后的取整边界附近，原先由单精度误差推到边界另一侧的落点，伤害取整结果可能改变。

## Realms 世界上传增加分块传输与服务端处理阶段

新版为本地世界上传加入可由服务端启用的新流程，改变分块、重试及何时视为上传完成。

### 差异出现的场景

将本地世界上传到 Realms。新版完整新流程仅在 Realms 服务端向该客户端返回 `v2upload` 功能标记时启用；没有该标记仍使用旧上传接口。

### 版本变化

- Snapshot 6：取得旧上传信息后打包并传输一个压缩包，上传完成后更新世界槽位配置。进度显示进入校验时，取消按钮会禁用。
- Snapshot 7：读取功能标记后先完成打包，再调用对应的上传流程。新流程建立上传会话，按服务端给出的单次上传大小、分块大小和分块数上限，选择整包或逐块传输；会话快过期时续期。传输完成后提交，并轮询服务端处理状态，确认完成后才更新槽位配置并结束上传。

创建或续期会话、传输文件或分块、查询处理状态遇到可重试的网络错误、HTTP 408、429 或 5xx 时，最多尝试 5 次，优先遵守 `Retry-After`。完成提交遇到瞬时失败时，会先查询处理状态，判断服务端是否已经接受提交。已经成功的前序分块不因某个后续块重试而全部重传；关闭客户端后重新开始上传的断点续传不在这套实现中。

新版界面区分上传、校验提交和处理中；新流程后两个阶段在处理尚未完成时仍可取消，取消会中断当前请求并尽力通知服务端。无论采用哪种流程，打包失败或取消时也会尝试删除打包阶段已创建的临时压缩包，避免这种失败留下大文件。

### 实际影响

具备新标记的 Realms 上传，在大文件或临时网络故障时使用不同的重试和完成判定。进度达到 100% 后仍可能需要等待服务端处理完成。客户端打包器原有的 5 GiB 检查仍保留，实际还受会话返回的大小上限约束。

## 默认图形 API 改为随机选择首选后端

图形 API 的首选次序决定客户端先尝试使用哪种渲染后端，本次同时调整默认次序和 Vulkan 设备筛选。

### 差异出现的场景

客户端图形 API 设置保持为 Default，启动时 OpenGL 与 Vulkan 都可能可用；或机器上的 Vulkan 设备曾被旧版名单排除、只有 CPU 实现可用。

### 版本变化

- Snapshot 6：Default 总是先尝试 Vulkan，再尝试 OpenGL；Vulkan 会拒绝一批列入已知问题名单的设备，也可以选择 CPU 设备。
- Snapshot 7：Default 每次取得候选后端时随机决定先试 OpenGL 还是 Vulkan，首选失败仍尝试另一种。显式选择 OpenGL 或 Vulkan 的优先次序不变。Vulkan 的问题设备名单清空，同时默认跳过 CPU 设备；提供 JVM 系统属性 `renderpearl.vulkan.allowcpudevice` 才允许 CPU 设备参与。

### 实际影响

保持 Default 的玩家，重启后实际使用的渲染后端可能不同。只暴露 CPU Vulkan 设备的环境默认会转而尝试 OpenGL；原来被名单拦截的设备则会进入其他兼容性检查。设备是否能够启动，仍取决于剩余兼容性检查。

## Vulkan 持续渲染不再泄漏通道清空参数的本地内存
