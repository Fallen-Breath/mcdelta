# Minecraft 1.20.3-pre4 变更分析

- 上一个版本：1.20.3-pre3
- 当前版本：1.20.3-pre4

## 容器交换操作限制为快捷栏和副手，封堵直接操作盔甲栏的异常请求

容器界面中的数字键和副手交换键，本应将鼠标指向的物品栏位与快捷栏或副手交换。新版限制了这类操作能够指定的交换目标，影响使用自定义客户端发送其他目标编号的操作。

### 差异出现的场景

玩家打开有效的容器界面，向服务器发送 `SWAP` 类型的点击请求，点击的容器栏位有效，但交换目标参数不是快捷栏的 `0–8` 或副手的 `40`。以下涉及取出物品的情况，还要求点击的容器栏位允许玩家取走物品。

### 版本变化

- 1.20.3-pre3：服务器直接把交换目标参数当作玩家物品栏的编号。`9–35` 可以直接交换主物品栏，`36–39` 可以直接交换盔甲栏；盔甲栏作为交换目标时，不经过该盔甲栏自身的物品类型、堆叠数量和绑定诅咒检查。例如，将普通物品所在的容器栏位与空的盔甲栏交换，可以把普通物品放进盔甲栏；将空的普通容器栏位与穿着绑定诅咒装备的盔甲栏交换，可以取下该装备。目标参数大于 `40` 时，读取结果为空、写回无效，因而会清空被点击栏位中原本可以取出的物品，使物品丢失；参数为负数时，则会访问负下标并产生容器点击异常。
- 1.20.3-pre4：只处理交换目标为 `0–8` 或 `40` 的请求，其余目标参数均被忽略。上述直接交换主物品栏、绕过盔甲栏限制、丢失物品和负下标异常的路径均被关闭。

原版客户端的快捷键本来就只发送 `0–8` 和 `40`，因此正常使用数字键或副手交换键的操作保持原有表现。

## 进度奖励函数中的 return 不再中断触发它的外层函数

数据包函数执行命令时，可以完成玩家进度并触发另一个奖励函数。新版修正这类间接调用的嵌套关系，使奖励函数结束时只停止自己的后续执行。

### 差异出现的场景

一个正在执行的数据包函数通过 `advancement grant` 等操作，完成带有函数奖励的进度；奖励函数执行了会结束自身执行的 `return`，包括 `return <值>`、`return fail` 或实际执行到的 `return run …`。进度必须在此次操作中完成并触发奖励，且外层函数仍有待执行的命令。

例如，外层函数先给当前玩家授予一个尚未完成的自定义进度，再执行 `say after`；该进度的奖励函数直接执行 `return 0`。

### 版本变化

- 1.20.3-pre3：奖励函数被按全新顶层函数安排执行，丢失了它与外层调用之间的嵌套关系。奖励函数执行 `return` 时，会一并丢弃队列中外层函数尚未执行的命令，还可能继续影响其他等待恢复的调用层。在上述例子中，`say after` 不会执行。
- 1.20.3-pre4：服务器记录当前命令所在的调用深度，将执行过程中间接启动的奖励函数安排在更深的调用层。奖励函数中的 `return` 只结束对应的奖励函数，随后继续执行外层剩余命令；上述例子的 `say after` 会执行。

这一变化修复了使用进度奖励函数处理事件的数据包中，奖励函数提前返回后连带跳过外层逻辑的情况。奖励函数自身位于 `return` 之后的命令，仍然不会执行。

## 多人游戏服务器列表恢复悬停提示

在多人游戏的服务器列表中，将鼠标移到连接状态图标，或有玩家名单的在线人数区域：1.20.3-pre3 会在绘制列表后立即清空刚生成的悬停提示，因此看不到延迟、连接失败、版本不兼容等状态说明，也看不到服务器提供的玩家名单。1.20.3-pre4 改为先清空提示、再绘制列表并显示本次生成的提示，这些信息恢复显示；玩家名单仍取决于服务器是否提供相应内容。
