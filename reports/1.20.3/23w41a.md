# Minecraft 23w41a 变更分析

- 上一个版本：23w40a
- 当前版本：23w41a

## 饰纹陶罐成为单格容器，并改变对陶罐使用物品的结果

原有饰纹陶罐现在可以存放一组物品，参与漏斗运输和比较器检测。这也改变了玩家对已有陶罐右键使用方块、工具等物品时的结果。

### 差异出现的场景

玩家不潜行，对饰纹陶罐使用手中的物品；或让漏斗、投掷器向陶罐输送物品，让下方漏斗抽取物品，并用比较器读取陶罐。

### 版本变化

- 23w40a：陶罐没有物品槽，不接受自动输入，不提供容器比较器信号。玩家的右键操作会继续交给手中物品处理，例如在陶罐旁放置方块。
- 23w41a：陶罐有一个物品槽。每次右键成功放入一个物品，已有内容时要求物品种类和标签相同，且未达到该物品的堆叠上限。创造模式会复制一个物品放入。漏斗和投掷器可以输入，漏斗可以抽出；比较器按该槽的填充比例输出信号，空罐为 0，装满为 15。

手动放入会播放声音、使罐体晃动并产生粒子。空手、物品不匹配或陶罐已满时，陶罐播放失败反馈；这些操作也会产生方块变化游戏事件。陶罐的交互始终消费这次操作，因此正常右键不再继续执行手中物品的放置等动作；潜行持物品时仍可绕过陶罐交互。陶罐没有物品栏界面，手动取出内容需要破坏陶罐，或使用漏斗。破坏时内容单独掉落，完整陶罐物品只保存四面装饰，不携带库存。

本版手动放入还有一个保存问题：该路径修改库存后没有将方块实体标记为需要保存。如果陶罐所在区块已经保存，之后也没有其他操作使该区块重新需要保存，那么卸载区块或正常关闭世界时可能跳过保存，重新加载后库存回到上次保存状态。漏斗输入会调用容器的保存通知，不属于这一条手动输入路径。比较器等设施产生的其他区块修改也可能使手动输入得到保存，因此不能概括为每次退出都会丢失。

## 投射物能够打碎已有陶罐，陶罐物品可堆叠至 64 个

23w40a 中，箭、雪球等投射物击中饰纹陶罐不会触发专门的碎罐处理。23w41a 中，属于 `minecraft:impact_projectiles` 标签的投射物命中时，陶罐会破碎，按碎罐规则掉落陶片或红砖，里面的物品也会掉出。原本用陶罐挡住发射器、箭道或雪球的布置因此会被破坏。

原版标签包含箭、雪球、鸡蛋、三叉戟以及几类火球和凋灵之首。破坏还要求投射物有权修改该位置：玩家投射物受玩家交互权限限制，生物所有的投射物受 `mobGriefing` 限制；没有所有者的投射物允许执行这一检查。末影珍珠和药水没有列入这个原版标签，不会通过本次新增的命中处理碎罐。

此外，相同装饰和物品标签的陶罐物品，堆叠上限从 1 提高到 64。已有运输、储存和比较器检测中，把一只陶罐当作不可堆叠物品的配置会改变填充比例。

## 南瓜重新响应剪刀雕刻

对普通南瓜使用剪刀，23w40a 中不会雕刻，因为该版本将南瓜注册成了普通方块。23w41a 恢复南瓜专用方块行为：南瓜变为雕刻过的南瓜，掉出四个南瓜种子，并消耗剪刀耐久。这恢复了手持剪刀的南瓜采种方式；本项指玩家交互，发射器剪南瓜不经过这个交互方法。

## 刷子的作用距离和实体遮挡更贴近实际瞄准

23w40a 中，刷子每次刷动会重新检测眼前 5 格范围，且检测实体时将其包围盒向外扩张 0.3 格。23w41a 改成生存等非创造模式 4.5 格、创造模式 5 格，并取消刷子检测中的这层实体扩张。

因此，生存玩家开始刷方块后退到 4.5 至 5 格之间，旧版仍可能继续刷到该方块，新版停止作用；站在可交互距离内、视线擦过附近实体但没有穿过其实际包围盒时，旧版实体可能挡住刷子，新版可以刷到后面的方块。飞行中的箭等投射物仍保留自己的 0.3 格命中余量，本次取消只用于刷子的视线检测。

## 刷过的可疑方块失去支撑时，更快开始下落

对尚未刷完的可疑沙子或可疑沙砾刷动一次后，再移除下方支撑方块，23w40a 可能要等待原先已经安排的刷扫检查，方块才开始下落。首次刷动安排的是 40 游戏刻后的检查；同一位置同种方块的计划刻会去重，移除支撑时新安排的两刻下落检查不能替换已有的较晚检查。

23w41a 将刷扫期间的检查统一改为每两游戏刻一次，下落判断也随这次方块刻执行。上述悬空方块因此通常在接下来的两游戏刻内开始下落，不能再利用刷扫后残留的长计划刻暂时将它悬空。方块落下仍按原有可疑方块规则破碎。

刷扫进度的回退条件本身仍是最后一次刷扫 40 游戏刻后开始回退，之后每四游戏刻减少两次进度；本次调整的实际装置影响来自共享方块刻中的下落检查。

## 给马类无效喂食不再白白消耗食物

生存玩家给已经不需要该食物的马、驴或骡喂食，例如给满血、已经驯服的成年马使用普通苹果或小麦，23w40a 仍会减少一件食物，即使这次操作没有治疗、促进成长、增加驯服进度或进入求爱模式。23w41a 只有食物确实产生效果才扣除物品；未产生效果时保留食物。

## 船与矿车放置时读取更多物品数据，破坏时的命名处理也改变

### 差异出现的场景

使用铁砧改过名的船，或使用命令制作带 `EntityTag` 的船、矿车物品，由玩家放置或由发射器生成；随后以攻击等伤害方式拆除这些载具。

### 版本变化

- 23w40a：船物品上的自定义名称不会应用到生成的船。矿车会应用物品名称，但两类载具都不读取物品的 `EntityTag`。普通伤害拆船得到的船物品不保留实体名称；创造玩家攻击有名字的矿车，会让它掉出对应矿车物品。
- 23w41a：船、运输船、竹筏和矿车在玩家放置及发射器生成时，都会应用物品自定义名称和允许写入的 `EntityTag`。例如预先配置箱内物品的运输船、箱子矿车，或带展示方块的矿车，可以通过对应物品生成。普通伤害拆掉的船会保留自定义名称；创造玩家攻击普通矿车时，即使矿车有名字，也直接移除而不掉出矿车本体。

实体数据仍按该实体的管理权限规则检查，命令方块矿车等要求管理员的实体不会因为由发射器生成就接受受限数据。船的材质和朝向在读入后仍按船物品种类、玩家或发射器方向设置。

TNT 矿车有独立后果：旧版创造玩家攻击无名 TNT 矿车时，会直接移除；新版会进入 TNT 矿车自己的受损处理。静止且受到普通伤害时可以掉出物品；在水平速度至少为每刻 0.1 格，或伤害属于火焰、爆炸时，会进入引燃处理。创造模式下攻击运动中的 TNT 矿车因而可能留下已引燃矿车。

这里的名称保留指受伤害拆除的掉落路径；船跌落破坏仍使用其原有木板和木棍处理。

## 通过维度传送复制实体时，更多所有者关联得以保留

非玩家实体通过传送门，或由命令跨维度传送时，会在目标维度创建实体并复制状态。23w41a 增加了复制物品投掷者、投射物发射者、已点燃 TNT 点燃者和恼鬼召唤者的处理。

- 23w40a：TNT 和恼鬼在复制后丢失运行中的所有者引用。投射物虽然保存发射者 UUID，但在目标维度找不到仍留在原维度的发射者时，不能恢复关联。掉落物也只能在自己当前维度通过 UUID 寻找投掷者。
- 23w41a：上述引用在复制时一并保留；投掷物品时还会直接缓存投掷者。只要缓存指向的实体仍有效，掉落物或投射物不必在目标维度重新找到对方，仍能知道是谁投出或射出。

这使跨维度 TNT 和投射物的伤害来源能够继续指向原点燃者、发射者；依赖玩家来源的机制也会随之改变。例如玩家投出的物品跨维度后，在满足幽匿尖啸体其余触发条件时，仍可被认作玩家造成的触发。恼鬼则保留用于追随召唤者攻击目标的关联。

这只是运行中跨维度复制时保留引用。TNT、恼鬼的这项引用没有因此获得完整的存档持久化；投射物和掉落物在缓存失效或重新读档后，也仍依赖 UUID 查找。末影珍珠本身另有跨维度清除发射者及同维度传送检查，本项不能据此推导玩家能被珍珠跨维度拉回。

## 函数结果改为由显式返回提供，影响命令方块与 execute store

函数调用改成在命令执行队列中安排，并在函数实际执行 `return` 时报告结果。它会改变已有数据包通过函数执行命令并读取结果的方式。

### 差异出现的场景

使用 `execute store result`、`execute store success` 包住 `/function`，或由命令方块执行函数并让后续条件制约型命令方块读取成功状态。

### 版本变化

- 23w40a：从外层直接执行函数时，没有显式返回的函数会以执行条目数作为结果；函数内部普通命令还继承调用者的结果回调。嵌套调用若被延后执行，调用语句先得到 0，随后子函数内部命令又可能更新继承的保存目标，结果容易被内部命令覆盖。
- 23w41a：调用函数时清除其内部普通命令继承的结果回调。只有执行到显式 `return`，才向调用者报告成功和返回整数；调用函数标签时会累加各函数显式提供的返回值，并在返回到达时更新调用者。

例如函数只有一条 `say ready`，外层用 `execute store result score out obj run function demo:test` 执行：旧版得到的函数结果为 1；新版函数可以正常说话，但没有返回值回调，`out` 保留原值。同理，命令方块执行一个没有显式返回的函数，内部命令虽然生效，成功计数仍可能为 0，后面的条件制约型命令方块不再仅凭函数有执行内容就启动。

已有函数需要向调用者提供结果时，应由函数返回该结果。显式 `return 0` 也会报告“执行成功、数值为 0”，不能把零数值等同于调用失败。标签内多个函数返回时，外层保存结果可能被连续写入累计值，而不是只在标签全部执行完后写一次。

## 进度奖励函数立即嵌入触发命令执行

### 差异出现的场景

一个正在执行的函数，通过命令或游戏行为授予带奖励函数的进度，例如执行 `execute store result score out obj run advancement grant @s only demo:reward`，而奖励函数会读取 `out`。

### 版本变化

- 23w40a：函数管理器发现已经有函数正在执行，就把奖励函数加入当前队列，待正在执行的命令返回后再运行。因此外层 `execute store` 先写入命令结果，奖励函数随后读取到该结果。
- 23w41a：这类由游戏系统调用的函数每次建立自己的执行队列，并在调用现场运行完毕。奖励函数会在授予进度的命令返回之前运行，上例中读取到的是 `out` 写入本次结果之前的值。

新队列也单独取得命令执行额度。反复撤销并重新授予进度、让奖励函数递归触发自身的配置，不再通过旧版共用函数队列限制这条递归链；它可能形成同步递归，带来卡顿或调用栈耗尽。普通 `function` 命令调用子函数仍在同一命令队列安排，不属于这里由进度奖励等系统重新进入函数管理器的路径。

## 新增 return run 和函数条件，直接 return 不再触发普通结果保存

- 23w40a 只有 `return <整数>`；23w41a 增加 `return run <命令>`。后面的命令提供结果时，会结束当前函数并将该整数作为返回值；普通命令执行失败并报告失败结果时返回 0。若后面的命令没有产生任何结果回调，例如选择器分支为空，则这一写法不会自动制造一个返回值。
- 新版 `return <整数>` 直接终止当前函数并报告函数返回值，不再同时报告一次普通命令结果。因此函数内写成 `execute store result score out obj run return 7`，旧版会把 7 写入 `out`，新版只返回，不通过这层普通结果回调写分数；`store success` 同样受影响。放在函数外的 `return` 也不会凭这一普通保存回调写入目标。
- 新版允许 `execute if function demo:test run ...` 和 `execute unless function demo:test run ...`。条件函数实际执行，`if` 接受非零显式返回，`unless` 接受零显式返回；没有执行到返回语句时，两种条件都不会继续后续命令。传入函数标签时会执行标签中的函数，只要其中一个返回符合条件，当前分支就继续一次，不因多个匹配返回而重复继续。这给已有函数增加了作为条件的用法，也意味着条件函数内的实际修改会发生。该语法不传入宏实参，需要参数的宏函数会在这里实例化失败。

## 命令执行预算覆盖分支，新增分叉上限，但本快照有边界缺陷

`maxCommandChainLength` 在旧版函数执行中主要按取出的函数条目计数。一行 `execute as @e run ...` 即使产生大量执行分支，也作为该行函数条目消耗额度；直接在聊天或命令方块执行的命令不会因此进入旧函数预算。

23w41a 将直接命令也放入统一执行队列。普通命令的每一个最终执行分支都会消耗额度；调用函数及准备 `execute` 的各个带执行源变换步骤也消耗额度。因此相同的函数和相同规则值下，大量选择器分支、更长的 `execute` 链及频繁子函数调用，可能更早耗尽额度，导致剩余操作没有执行。直接命令也受这一预算约束。当前队列一旦因额度停止，没有执行的部分不会留到下一刻自动续跑。将规则设为 0 时，旧版非空函数仍会先执行第一条再停止，新版在执行队列任何一项之前便停止。

新版另增默认 65536 的 `maxCommandForkCount`，检查单条命令在准备某一步后积累的执行源数量。本快照使用“大于或等于上限”作为拒绝条件，所以默认实际只能接受至多 65535 个执行源；把它设成 1 时，一个带源变换、结果仍只有一个执行源的步骤也会被拒绝。达到上限时，该步骤不会执行最终命令，而不是截取前若干个实体继续运行。

本快照的预算检查还有一个缺陷：队列仅在下一项开始前检查额度是否**恰好等于 0**，而一项准备工作可以连续扣除多个 `execute` 步骤的额度。若同一项准备把额度从正数越过零减成负数，后续执行便会绕过这次额度停止检查。因而不能把本版 `maxCommandChainLength` 当作对任意复杂 `execute` 链都可靠的严格上限。普通分支没有发生这种越零时仍按上述规则停止。

## 函数加载、执行错误和调试输出的处理改变

- 函数文件中只写了一个尚未形成可执行命令的行，例如单独的 `execute`，旧版可能通过加载，执行到该行才失败并继续后面的行。新版加载时要求能构成最终可执行命令，该函数会直接加载失败；宏替换产生这类不完整命令时，也会在实例化阶段拒绝整个函数调用。
- 对空函数标签执行 `function #demo:empty`，旧版按返回结果 0 的成功命令完成；新版将它作为没有函数可安排的错误，`execute store success` 因而从 1 变为 0。
- 执行函数标签时，如果其中一个宏函数缺少参数或替换后语法无效，旧版报告该项错误后继续尝试标签里的后续函数。新版会抛出调用错误并停止继续安排剩余函数；在出错前已经安排的函数仍会运行，所以并不是整组回滚。
- 聊天或命令方块直接运行的命令，如果语法解析成功，但在执行阶段抛出错误，例如控制台执行需要玩家身份的命令，旧版会由命令入口发送错误反馈。新版执行队列捕获这些异常后，通常只供 `/debug function` 的跟踪器记录，不再由同一入口向玩家发送错误文字。语法解析阶段的错误仍会显示；`function` 和调试函数的自定义执行器另有显式错误反馈，不能概括为所有错误一律消失。
- `/debug function` 成功反馈里的命令数量，旧版按实际执行取出的函数条目累计，新版按直接选中的函数所含条目数相加。提前返回、调用子函数或大量分支时，这个数字不再代表实际发生的命令执行次数。

## Realms 增加配对的快照世界与实验选项

23w40a 客户端没有专门的快照 Realm 创建入口。23w41a 在快照客户端中请求服务端提供可创建快照世界的 Realm 列表，并允许为符合服务端条件的正式 Realm 创建配对的快照 Realm。配对世界通过新世界生成流程创建，正式 Realm 在快照列表中作为不能直接进入的关联条目展示，而不是直接把正式世界当作快照世界打开。具体账号是否有资格及配对限制由 Realms 服务端决定，本地源码没有承诺所有订阅都可用。

进入快照 Realm 还会根据服务端返回的版本兼容状态处理：兼容时直接连接；需要升级、降级或无法验证时显示确认；非拥有者只有兼容时才能启用游玩。创建或重置生成型 Realm 世界时，界面新增实验选项，并将选择的功能数据包名单发送给服务端。

普通新 Realm 的初始化时机也后移：旧版输入名字继续后便提交初始化，再选择世界；新版先选择要生成或使用的世界，确认后才按顺序初始化和生成。因此在选世界阶段返回，不再已经提交初始化。

## 命名显示、盾牌姿态与交互声音

- 对着有自定义名称的船、矿车等非生物实体时，新版可以显示其名称；旧版准星专门记录生物或物品展示框，基础实体名称显示又要求强制显示名称，普通命名载具的名字不会以同样方式在瞄准时出现。基础渲染路径中设置了 `CustomNameVisible` 的实体，即使没有自定义名称，新版也可显示其默认实体名称；旧版还要求确实存在自定义名称。生物渲染器自身的队伍和可见性规则仍会参与它们的名称显示。
- 玩家举盾后大幅转头时，旧版持盾手臂的水平角度随头部一起继续旋转；新版将头部对盾牌姿态的水平影响限制在左右各 30°，改变第三人称姿态。
- Realms 的加载文字组件不再参与键盘焦点切换，点击它也不再播放普通按钮点击声；旧版将这一加载组件作为普通可聚焦组件处理。
- 对打蜡悬挂式告示牌进行不能修改文字的交互时，新版播放悬挂式告示牌专用的失败声音，旧版使用普通告示牌的声音。

## GameTest 批次和成功后的清理

开发测试世界中，23w40a 每批最多放入 100 个 GameTest，成功后保留测试里的实体。23w41a 每批最多 50 个，且测试成功时会移除测试结构包围盒向外扩大一格范围内的所有非玩家实体，包括掉落物、载具和生物。依赖成功后留在场内的实体继续观察，或让它们参与后续测试的配置，会受到这次清理影响；测试失败不经过新增的成功清理路径。

数据包格式同时从 19 提高为 20，资源包格式仍为 18，影响使用本版函数规则的数据包声明与兼容性提示。
