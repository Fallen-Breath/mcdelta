# Minecraft 23w41a 变更分析

- 上一个版本：23w40a
- 当前版本：23w41a

## 饰纹陶罐成为单格容器，并截住正常右键操作

饰纹陶罐新增一个物品槽，可以接入物品运输和比较器检测。玩家对陶罐正常右键时，也会先尝试往罐中放入物品。

### 差异出现的场景

玩家不潜行，对饰纹陶罐使用手中物品；或用漏斗、投掷器向陶罐输入物品、用下方漏斗抽取，并用比较器读取库存。

### 版本变化

- 23w40a：陶罐没有物品槽，不接受自动输入，也不提供容器比较器信号。右键操作会继续交给手中物品处理，例如在陶罐旁放置方块。
- 23w41a：陶罐可存放一组物品。每次右键成功放入一个，已有内容时要求物品种类和标签相同，且未达到该物品的堆叠上限；创造模式会复制一个放入。漏斗、投掷器可以输入，漏斗可以抽出。比较器按该槽填充比例输出信号，空罐为 0，装满为 15。

23w41a 手动放入成功时会播放声音、晃动罐体并产生粒子；空手、物品不匹配或已满时会播放失败反馈。这些交互都会产生方块变化游戏事件，并消费本次操作，因此正常右键不再继续执行手中物品的放置等动作。潜行持物品时仍可绕过陶罐交互。

陶罐没有物品栏界面，取出内容要用漏斗或破坏陶罐。破坏时内容单独掉落，完整陶罐物品只保存四面装饰，不携带库存。

## 手动放入陶罐的物品可能未随区块保存

新增的陶罐手动输入路径没有将方块实体标记为需要保存。这个遗漏会影响已经保存过、之后又没有其他修改的区块。

### 差异出现的场景

陶罐所在区块已经完成保存，玩家随后手动放入物品；在区块卸载或正常关闭世界前，没有其他操作让该区块重新需要保存。

### 版本变化

- 23w40a：陶罐不能存放物品，没有这条手动输入和库存保存路径。
- 23w41a：手动输入虽然立即生效，但可能因为区块跳过保存而没有写入存档。重新加载后，库存会回到上次保存状态。

23w41a 的漏斗输入会调用容器保存通知，不属于上述遗漏。比较器等设施造成的其他区块修改，也可能让手动输入一并得到保存；因此问题只出现在上述保存条件下。

## 投射物命中可以打碎饰纹陶罐

饰纹陶罐新增投射物命中处理，原本用于阻挡箭或雪球的陶罐会因此破碎。

### 差异出现的场景

属于 `minecraft:impact_projectiles` 标签的投射物命中陶罐，且有权修改该位置。玩家所有的投射物受玩家交互权限限制，生物所有的投射物受 `mobGriefing` 限制；没有所有者时允许通过这项权限检查。

### 版本变化

- 23w40a：命中不会触发专门的碎罐处理。
- 23w41a：陶罐破碎，按碎罐规则掉落陶片或红砖，罐内物品也会掉出。

原版标签包含箭、雪球、鸡蛋、三叉戟、几类火球和凋灵之首。末影珍珠和药水不在此标签内，不会通过这次新增的命中处理碎罐。

## 饰纹陶罐物品的堆叠上限提高至 64

饰纹陶罐物品改用默认堆叠上限，改变运输、储存和容器比较器检测中的填充比例。

### 差异出现的场景

将装饰和物品标签相同的陶罐物品放进同一容器槽位，或用比较器读取装有陶罐的容器。

### 版本变化

- 23w40a：每槽最多放一个陶罐，一个陶罐即可填满该槽。
- 23w41a：每槽最多堆叠 64 个陶罐；一个陶罐只占该槽容量的六十四分之一。原先把陶罐当作不可堆叠物品的检测配置会读到不同的填充比例。

## 南瓜重新响应剪刀雕刻

南瓜恢复使用专用方块行为，玩家可以再次用剪刀雕刻并取得种子。

### 差异出现的场景

玩家手持剪刀对普通南瓜使用；发射器剪南瓜不经过这条玩家交互路径。

### 版本变化

- 23w40a：南瓜注册为普通方块，使用剪刀不会雕刻。
- 23w41a：南瓜变为雕刻过的南瓜，掉出四个南瓜种子，并消耗剪刀耐久。

## 刷子的作用距离和实体遮挡判定改变

刷子每次刷动都会重新检测瞄准目标。新版按玩家模式决定检测距离，并取消这条视线检测对实体包围盒的额外扩张。

### 差异出现的场景

非创造模式玩家开始刷方块后，退到目标距离 4.5 至 5 格之间；或在可交互距离内，让视线擦过附近实体、但不穿过其实际包围盒，瞄准后方可疑方块。

### 版本变化

- 23w40a：刷子检测距离固定为 5 格，退到上述范围仍可能刷到方块；实体包围盒向外扩张 0.3 格，擦过实体旁边的视线也可能被挡住。
- 23w41a：非创造模式检测距离为 4.5 格，创造模式为 5 格，前一种情形停止作用。实体检测不再额外扩张 0.3 格，后一种情形可以刷到后面的方块。

这次取消扩张只影响刷子的视线检测；飞行中的箭等投射物仍保留自己的 0.3 格命中余量。

## 刷过的可疑方块失去支撑时更快下落

刷扫检查与可疑方块的下落判断共用计划方块刻。新版缩短刷扫期间的检查间隔，移除了旧版利用较晚检查暂时维持悬空状态的条件。

### 差异出现的场景

对尚未刷完的可疑沙子或可疑沙砾刷动一次，随后移除下方支撑。

### 版本变化

- 23w40a：首次刷动安排 40 游戏刻后的检查。同一位置、同种方块的计划刻会去重，移除支撑时安排的两刻下落检查不能替换已有的较晚检查，因此可能要等到原来的刷扫检查才下落。
- 23w41a：刷扫期间统一每两游戏刻检查一次，下落判断也随之执行。上述方块通常会在接下来的两游戏刻内开始下落，并按可疑方块原有规则破碎。

刷扫进度仍从最后一次刷扫 40 游戏刻后开始回退，之后每四游戏刻减少两次进度；本次悬空行为的差异来自共用方块刻中的下落检查。

## 拆除酿造台时补发比较器更新

酿造台移除时改用共用容器掉落处理，除了掉出内容，还会通知读取它的比较器重新计算。

### 差异出现的场景

替换或拆除酿造台，并让比较器直接读取它，或隔着一块导体读取它。

### 版本变化

- 23w40a：会掉出内容，但没有专门通知比较器；比较器可能保持旧信号，直到收到其他更新。
- 23w41a：掉出物品后补发比较器通知，相关比较器会因酿造台移除及时重新计算。

箱子、木桶、漏斗和发射器也改用这个共用方法，但原本已有同类通知。

## 给马类无效喂食不再消耗食物

马、驴和骡的喂食现在按是否产生效果决定扣除物品。

### 差异出现的场景

生存玩家使用食物喂马、驴或骡，但这次操作不能治疗、促进成长、增加驯服进度或进入求爱模式，例如给满血、已驯服的成年马使用普通苹果或小麦。

### 版本变化

- 23w40a：即使没有产生上述效果，仍减少一件食物。
- 23w41a：只有食物确实产生效果时才扣除；上述无效喂食会保留食物。

## 船与矿车放置时读取物品名称和实体数据

船与矿车的生成配置改为统一读取物品名称及允许写入的实体数据，影响玩家放置和发射器生成的载具。

### 差异出现的场景

放置用铁砧改过名的船，或使用带 `EntityTag` 的船、矿车物品，由玩家或发射器生成载具。

### 版本变化

- 23w40a：船物品名称不会应用到生成的船；矿车会应用物品名称。两类载具都不读取物品的 `EntityTag`。
- 23w41a：船、运输船、竹筏和矿车都会应用物品自定义名称及允许写入的 `EntityTag`。预先配置箱内物品的运输船、箱子矿车，或带展示方块的矿车，可以由相应物品生成。

实体数据仍受各实体的管理权限规则限制，命令方块矿车等要求管理员的实体不会因为由发射器生成就接受受限数据。船的材质和朝向在读入后，仍按物品种类以及玩家或发射器方向设置。

## 函数结果由显式返回提供，改变命令方块和结果保存

函数调用改为在命令队列中安排，并在函数实际执行 `return` 时报告结果。这会改变调用者读取函数结果和成功状态的方式。

### 差异出现的场景

用 `execute store result`、`execute store success` 包住 `/function`，或让命令方块执行函数，并由后续条件制约型命令方块读取成功状态。

### 版本变化

- 23w40a：从外层直接执行时，没有显式返回的函数以执行条目数作为结果，内部普通命令还继承调用者的结果回调。嵌套调用被延后时，调用语句先得到 0，随后子函数命令又可能覆盖保存目标。
- 23w41a：调用函数会清除其内部普通命令继承的结果回调。只有显式 `return` 才向调用者报告成功和返回整数；函数标签会累加各函数显式返回的值，并在返回到达时更新调用者。

例如函数只有 `say ready`，以 `execute store result score out obj run function demo:test` 执行时，23w40a 的函数结果是 1；23w41a 仍会说话，但不提供返回值回调，`out` 保留原值。命令方块执行没有显式返回的函数时，内部命令虽然生效，成功计数仍可能为 0，后面的条件制约型命令方块不再仅凭函数有执行内容就启动。

23w41a 显式 `return 0` 仍报告执行成功，只是数值为 0。标签中多个函数返回时，外层保存目标可能被连续写入累计值，并非只在整组执行完后写一次。

## 进度奖励函数在触发命令返回前立即执行

进度奖励等游戏系统调用函数时，新版每次创建并运行自己的执行队列，改变了奖励函数与触发命令结果保存的先后顺序。

### 差异出现的场景

一个正在执行的函数授予带奖励函数的进度，例如执行 `execute store result score out obj run advancement grant @s only demo:reward`，而奖励函数会读取 `out`。

### 版本变化

- 23w40a：已有函数执行时，奖励函数加入当前队列，等触发命令返回后再运行。外层 `execute store` 先写入命令结果，奖励函数随后读取到该值。

## execute 可以用函数显式返回值判断条件

新增函数条件会实际运行指定函数，再按显式返回值决定是否执行后续命令。

- 23w40a：不接受这类函数条件语法。

## 命令执行额度覆盖分支和直接命令

`maxCommandChainLength` 改为限制统一命令执行队列，扣除方式也从函数条目扩展到执行准备、函数调用和最终分支。

### 差异出现的场景

在相同规则值下执行带大量选择器分支、较长 `execute` 链或频繁子函数调用的函数，或从聊天、控制台、命令方块直接执行命令。

### 版本变化

- 23w40a：函数预算主要按取出的函数条目计数，`execute as @e run ...` 即使产生大量分支，也作为一行消耗额度。直接命令不因此进入函数预算。规则为 0 时，非空函数仍先执行第一条再停止。
- 23w41a：每个普通命令的最终分支、函数调用和各个带执行源变换的准备步骤都会扣除额度，直接命令也受限。相同配置可能更早耗尽额度，剩余操作不执行，也不会留到下一刻续跑。规则为 0 时，在执行队列任何一项前便停止。

23w41a 的停止检查存在边界缺陷：仅在下一项开始前检查额度是否恰好为 0，而同一项准备工作能连续扣除多个 `execute` 步骤的额度。如果一次准备把正数越过零扣成负数，后续执行会绕过停止检查。因此本版额度对任意复杂 `execute` 链并非可靠的严格上限；未发生越零时仍按上述规则停止。

## 新增命令分叉上限，达到上限即拒绝该步骤
