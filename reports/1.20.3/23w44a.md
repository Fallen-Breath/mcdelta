# Minecraft 23w44a 变更分析

- 上一个版本：23w43b
- 当前版本：23w44a

## 地图、记分板等独立数据无法首次保存

新版修改了 NBT 文件的写入方式。直接保存到尚不存在的文件时，写入会失败，影响多种需要跨重启保留的世界数据。

### 差异出现的场景

世界需要第一次保存某个独立数据文件，例如新地图对应的 `data/map_<编号>.dat`、首次建立的记分板、某个命名空间的命令存储，或此前没有保存过的强制加载区块列表。旧世界也可能遇到此问题，条件是这次保存的具体文件尚不存在。

### 版本变化

- 23w43b：写入时可以创建文件，地图图像、记分板、命令存储等能够在退出世界后重新读取。
- 23w44a：写入要求目标文件已经存在。首次保存会报错，数据仅留在当前运行中的内存里；保存失败后仍会清除待保存标记。

这一变化也影响地图编号计数、袭击状态和命名随机序列。已有对应文件的数据仍可更新；世界信息和玩家数据的保存会先创建临时文件，因此不符合上述“目标文件不存在”的触发条件。

### 实际影响

新生成的地图可能在重进世界后失去图像；如果地图编号计数文件也从未建立，之后创建的地图还会再次使用先前的编号。首次保存失败的记分板、命令存储和强制加载列表会在重启后丢失；命名随机序列则会从重新初始化的状态继续生成随机结果。是否出现这些后果，取决于对应文件是否已由旧版或其他途径建立。

## 已保存的服务器列表和创造模式快捷栏不再载入

同一次 NBT 文件读写调整还把未压缩文件的存在性判断反转。服务器列表和已保存的创造模式快捷栏都会受到影响。

### 差异出现的场景

游戏目录中已有正常的 `servers.dat` 或 `hotbar.nbt`，随后在新版中重新读取服务器列表，或第一次访问已保存的创造模式快捷栏。

### 版本变化

- 23w43b：文件存在时读取其中的服务器条目或九组快捷栏。
- 23w44a：文件存在时直接当作没有数据，服务器列表显示为空，保存的快捷栏也以空组开始。

没有 `hotbar.nbt` 时，新版保存快捷栏还会因为无法创建目标文件而失败。当前游戏进程中的快捷栏仍会更新，重启后不会恢复。已有该文件时能够写入，但保存过程会把当前内存中的九组快捷栏全部写回；未重新建立的旧分组会被空组覆盖。

服务器列表使用预先创建的临时文件保存，因此本次添加的服务器可以写入磁盘，但再次载入列表时仍会被忽略。保存当前空列表或重新建立的列表，也会替换原来保存的列表。

## 饰纹陶罐支持延迟生成战利品

饰纹陶罐现在可以像箱子一样保存战利品表和随机种子，影响通过命令、物品数据或结构模板配置的陶罐。

### 差异出现的场景

为空饰纹陶罐设置 `LootTable` 和可选的 `LootTableSeed`，随后让玩家尝试放入物品、让漏斗读取或取出物品、使用比较器读取容量，或破坏陶罐。

### 版本变化

- 23w43b：陶罐只读取实际存储的物品，忽略战利品表字段；上述操作不会根据战利品表生成内容。
- 23w44a：陶罐保存战利品表，首次读取、取出或设置槽位内容时生成物品。生成后清除战利品表，后续操作使用已生成的物品。

陶罐依然只有一个槽位，战利品表生成多组物品时，无法放入该槽位的额外物品不会全部保存。这些触发入口没有向战利品表传入玩家，因此玩家幸运值和依赖玩家实体的条件不会因玩家亲手操作而自动生效。

结构模板放置也开始为陶罐重新生成战利品随机种子。模板中陶罐的固定种子会被替换；由于每个带方块实体数据的陶罐会额外消耗一次随机数，同一模板、同一放置种子下，后续箱子等容器得到的战利品种子也可能改变。

## 切制铜块可以直接切制成雕纹铜块

切石机新增从切制铜块制作雕纹铜块的配方，已有切制铜块库存可以直接用于这项加工。

### 差异出现的场景

世界启用 1.21 实验性内容，玩家将切制铜块或其氧化、涂蜡变种放入切石机。

### 版本变化

- 23w43b：不能从切制铜块直接选择制作雕纹铜块。
- 23w44a：每个切制铜块可以切制成一个雕纹铜块；四种氧化程度及各自的涂蜡变种均可转换，产物保留对应的氧化和涂蜡状态。

## 紫颂果传送音效集中到传送终点

紫颂果成功传送时的音效改为只从终点播放，同时调整传送玩家本人接收音效的方式，以及狐狸音效所属的音量类别。

### 差异出现的场景

玩家或狐狸食用紫颂果并成功传送，自己或附近玩家根据声音判断传送位置；狐狸的音效还受分类音量设置影响。

### 版本变化

- 23w43b：原位置播放一次传送声，实体又在终点向其他玩家播放一次。传送玩家本人不会通过终点的实体音效入口接收声音。狐狸在原位置播放的那次声音归入“玩家”音量类别。
- 23w44a：只在终点播放一次，传送玩家本人也会直接收到终点音效。狐狸的终点音效统一归入“友好生物”音量类别。

## 结构方块加载时替换作者信息，并减少尺寸同步

结构方块加载模板时会更新作者和结构尺寸。新版会清除空模板作者对应的旧信息，同时移除了加载过程中一次尺寸变化同步。

### 差异出现的场景

同一个结构方块先前保存着作者信息，随后加载没有作者信息的模板；或者通过红石加载与原尺寸不同的模板，并在客户端显示结构边界框。

### 版本变化

- 23w43b：空作者模板不会覆盖结构方块原来的作者。加载导致结构尺寸变化时，会立即向客户端同步新尺寸。
- 23w44a：作者总是替换为模板的作者，模板作者为空时清空旧作者。加载本身只更新服务器中的尺寸；红石加载后若没有其他同步更新，客户端边界框可能仍保留旧尺寸。

通过结构方块界面点击加载时，处理界面操作的入口会另行发送更新，因此该入口仍能同步尺寸。

## return 开始写入命令结果，并支持失败返回

函数返回值现在同时携带命令成功状态，并通知已经设置的结果存储。新版还提供显式失败返回，但函数调用是否抑制输出仍会影响外部读到的成功状态。

### 差异出现的场景

使用 `execute store result` 或 `execute store success` 包裹 `return 5`，直接让命令方块执行 `return 5`，或者在函数中显式返回失败。

### 版本变化

- 23w43b：`execute store ... run return 5` 只传递函数返回值，不会向该命令设置的结果存储提交 5 或成功状态；直接执行 `return 5` 的命令方块成功次数为 0。没有 `return fail` 语法。
- 23w44a：成功返回 5 时，结果存储得到 5，成功状态存储得到 1；直接执行 `return 5` 的命令方块成功次数为 1。新增的 `return fail` 以数值 0 和失败状态结束当前函数；`return 0` 仍是成功返回数值 0。

在 23w44a 中，从聊天或命令方块直接调用单个含 `return fail` 的函数时，函数结果反馈的包装会把失败改成成功，外部 `execute store success` 因而得到 1。同一调用发生在已抑制输出的函数内部时，得到 0。这取决于调用源是否抑制命令输出，与聊天反馈游戏规则无关。

## return run 保留结果存储，并立即结束当前函数

`return run` 用后续命令的结果结束函数。新版在进入该命令时就丢弃当前函数剩余行，保留此前设置的结果存储，并开始传递失败状态。

### 差异出现的场景

在函数中用 `execute store ... run return run ...` 记录结果；或者执行 `return run execute ... run ...` 时，后续条件不通过、选择器找不到目标，或最终命令抛出命令错误。

### 版本变化

- 23w43b：`return run` 会替换此前已经设置的结果存储。它在收到后续命令结果后才结束函数，因此条件或选择器未产生执行分支时，函数可能继续执行下一行。返回过程只转交整数，最终命令报错产生的 0 仍可能被外层函数调用记为成功。
- 23w44a：此前设置的结果存储得到保留，成功返回 5 时可写入结果 5、成功值 1。进入 `return run` 后立即丢弃当前函数剩余命令；后续没有执行分支时，以失败、数值 0 返回。在函数内部调用的路径上，最终命令报错也会保留失败状态，结果和成功值均为 0。

例如，函数中的 `return run execute if entity @e[tag=不存在的标签] run ...` 在没有匹配实体时，新版也会结束函数。外层直接调用单个函数时，失败状态还受上一条所述的输出包装影响。

## 函数标签调用改为最后汇总一次结果

普通 `function #标签` 仍会依次调用标签内的函数，但结果写入的时机和命令方块计数发生变化。

### 差异出现的场景

标签中至少有两个函数显式返回数值，并使用 `execute store ... run function #标签` 记录结果，或由命令方块执行该标签。例如两个函数分别执行 `return 5` 和 `return 7`。

### 版本变化

- 23w43b：第一个函数返回后立刻写入 5，第二个返回后写入累计值 12；命令方块因此收到两次成功，成功次数为 2。
- 23w44a：所有成员调用结束后才一次写入总和 12，命令方块成功次数为 1。成员函数的返回反馈分别显示本函数的结果，后一个不再显示先前成员的累计值。

### 实际影响

利用比较器读取命令方块成功次数的装置会得到不同强度。标签后面的函数如果读取同一次调用正在写入的分数、存储或 Boss 栏，也不能再依靠前面成员已经把中间累计值写入。

## if function 与 unless function 由第一个返回值决定

函数条件改为一次独立调用：首个显式返回结束这次条件求值；所有成员都没有返回时，按数值 0 判断。

### 差异出现的场景

使用 `execute if function` 或 `execute unless function` 检查函数标签。例如标签中第一个函数执行 `return 0`，第二个函数执行 `return 7`。另一个场景是被检查的函数正常执行到末尾，没有任何 `return`。

### 版本变化

- 23w43b：标签各成员都可以继续执行，只要其中一个返回值符合条件，就能保留执行分支。上例中第二个函数仍会执行，`if function` 与 `unless function` 两种检查都能通过。单个函数没有返回值时，不会提交条件结果，两种检查都不能继续后面的命令。
- 23w44a：上例在第一个成员返回 0 时结束，第二个成员不再执行；`if function` 不通过，`unless function` 通过。单个函数正常结束却没有返回时，补交 0，因此 `unless function` 可以继续。标签中未显式返回的成员不会立即终止条件求值，会继续尝试后面的成员。

新版在这里把成功返回的 0 和 `return fail` 都按 0 判断。补交 0 也适用于无法展开的宏函数：直接检查一个需要参数却没有收到参数的宏函数时，两版都会报告缺少参数；旧版 `unless function` 不继续，新版仍会按 0 让该条件通过。

### 实际影响

把函数标签当作一组都会执行的检查或副作用操作时，后面的成员可能因前面的显式返回而不再运行。标签成员顺序现在直接决定条件结果。
