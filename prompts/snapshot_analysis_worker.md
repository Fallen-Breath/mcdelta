# Minecraft 快照变更分析指引

## 需求背景

为熟悉 Minecraft 的读者分析一次快照更新对已有玩法和装置的影响。根据 `task.json` 中对应条目的目标与基准版本及两端完整源码目录，比较指定版本。报告应说明相同操作、装置配置或世界状态在新旧版本中产生的实际表现差异，以及这些差异对已有用法的影响。新增内容在影响已有机制时纳入分析。

文案、翻译和贴图修改不纳入分析范围。若该版本没有符合范围的游戏表现变化，简要说明即可，无需凑写修改条目。

检查完整变更范围，结合新旧源码和数据确认实际影响。正常执行、异常处理及跨系统调用都属于分析范围，底层修改需要追踪到游戏表现。对影响结论的疑点继续查清；只有确实复杂到需要超出本次任务的专项研究或实验时，才保留明确的未决问题。

临时文件保存在指定的分析工作目录，报告保存到指定路径。

## 变更点优先级

按变化对已有玩法的实际影响判断优先级并安排先后，综合考虑影响范围和对既有用法的后果。无需逐类覆盖或按下表分类组织报告。

| 优先级 | 分类 | 简要描述 |
| --- | --- | --- |
| 重点 | 已有方块与物品机制 | 已有行为变化，以及对玩家操作和装置的影响。 |
| 重点 | 已有实体与玩家机制 | 已有实体行为、运动和战斗等机制的变化。 |
| 重点 | 已有地形生成的修改 | 已有生成规则、生成结果及旧世界衔接的变化。 |
| 次重点 | 网络协议机制变化 | 改变实际联机行为的协议修改。 |
| 次重点 | 管理配置能力 | 配置、权限和管理能力变化，以及对世界运行的影响。 |
| 不重要 | 界面与显示调整 | 仅改变界面或画面表现，实际功能逻辑不变。 |
| 不重要 | 命令与数据包常规调整 | 常规接口扩展、语法和数据格式调整。 |
| 不重要 | 协议细节调整 | 版本号、数据表示或局部容错调整，联机行为基本不变。 |

## 行文指引

- **条目组织**
  - 按游戏机制组织条目，标题概括修改主题，同一机制的相关变化放在一起。
  - 条目默认采用完整结构；只有优先级为“不重要”且内容简单的修改可以用列表简述。
  - 篇幅取决于解释需要，完整条目的各栏目也可以简短。多项简述只有共享具体机制或使用场景时才合并。

- **信息取舍**
  - 先确定每项修改最值得说明的版本差异，围绕这一重点选择信息。
  - 背景与工作原理用于帮助读者理解变化。仅仅相关的事实，以及无助于解释差异的未变化行为，无需收录。
  - 涉及多个差异时，说明它们之间的关系，使读者能分辨主要变化、必要解释和直接后果；避免将相关事实逐项堆放。
  - “实际影响”只展开值得单独解释的直接后果。版本对比已充分表达时，省略整个栏目，避免为填写栏目而重复内容或追加建议、提醒。

- **差异说明**
  - 在相同条件下说明旧版与新版分别怎样。补充工作方式时，明确版本归属及其与本次差异的关系。
  - 将触发条件与必要的适用限制写在对应结论附近，影响描述应与源码支持的范围一致。
  - 尚未确定的具体影响在对应位置说明，区分已确认事实与推断。

- **语言表达**
  - 正文用自然语言描述游戏中的对象、动作和结果，使读者能够直接理解源码变化对应的游戏行为。
  - 游戏名称使用已确认的官方译名，无法确认时保留原名。避免逐字翻译代码概念或自行编造术语、简称。
  - 交代清楚谁对什么执行了什么动作，以及必要条件。指代应当明确，条件与结果之间应有清楚的衔接，避免为了省字而省略必要的句子成分。

- **叙述与排版**
  - 客观、直接地陈述结论，避免反问、设问，以及通过纠正假想误解来说明变化或范围。
  - 调查经过、核查记录和通用工作状态无需写入正文。
  - 列表用于表达确有并列关系的内容；新旧表现使用无序列表，加粗仅用于少量必要强调。

## 代码出处

- 在条目末尾用无序列表列出出处，格式为 `- <简短说明> [<版本>](<出处地址>)`。同一条目内说明相同的出处合并为一行，多个 Markdown 链接用“、”分隔。
- 同一行内，同一版本有多个链接时，按出现顺序标为 `[<版本> (1)]`、`[<版本> (2)]` 等；各版本分别从 1 编号，只有一个链接的版本不加编号。
- `task.json` 顶层的 `source_github` 非空时，使用 Markdown 链接，地址为：
  `<source_github>/blob/<对应版本的提交哈希>/<源码相对路径>#L<行号>`。
- `source_github` 为空时，链接地址使用相对于本地源码仓库根目录的路径和行号，格式为 `<源码相对路径>:<行号>`，路径以 `/` 分隔。
- 引用旧版行为时，使用基准版本的提交与行号。

下方成品用于理解栏目内容、表达和详略，报告结构以格式模板为准。示例中的版本、修改内容及代码出处均不作为本次任务的分析目标或事实依据，无需为核查示例查阅源码。

## 随机传送增加世界边界碰撞检查

紫颂果和末影人的随机传送在选定落点时，会检查目标位置是否容得下实体。新版增加了身体与世界边界的碰撞检查，影响边界附近的落点选择。

### 差异出现的场景

随机传送选出的落点中心位于世界边界内，但实体放到该处后，身体的一部分会超出边界。

### 版本变化

- Snapshot 3：落点检查只限制目标中心的位置。在满足其他落点条件时，可以接受身体部分越界的位置。
- Snapshot 4：落点检查同时考虑实体身体与世界边界的碰撞，拒绝上述位置。

代码出处：

- 随机传送落点检查 [26.4-snapshot-4](src/main/java/net/minecraft/world/entity/LivingEntity.java:3720)
- 世界边界碰撞检查 [26.4-snapshot-4](src/main/java/net/minecraft/world/level/CollisionGetter.java:59)

## 唱片机新增箱子轮播模式

唱片机可以自动播放上方箱子中的唱片，改变了已有自动播放器的换片和停止播放方式。

### 差异出现的场景

唱片机正上方紧贴普通箱子、陷阱箱或铜箱，包括铜箱的氧化及涂蜡状态。箱子必须为单箱，箱内存放可播放的唱片。

### 版本变化

- Snapshot 3：上方箱子仅用于储物。唱片播放结束后，唱片机停止播放并保留唱片，播放信号降为 0。
- Snapshot 4：空唱片机会自动从上方箱子取片。唱片播放结束后，自动换入下一张；箱内没有其他唱片时，重复播放当前唱片。

新版按箱子槽位顺序循环寻找下一张唱片，跳过普通物品。换片时，当前唱片与下一张唱片所在槽位的物品交换。

新版还调整了播放结束时的处理顺序：先完成换片或重新播放，再向相邻方块发出更新。正常轮播期间，相邻电路读取到的播放信号保持为 15。

### 实际影响

- 箱内唱片的位置会随播放过程变化，依赖固定槽位存取特定唱片的装置需要相应调整。
- 利用播放信号从 15 降为 0 来检测唱片播放结束的电路，在箱子轮播模式下失去这一触发条件。
- 玩家或漏斗取出当前唱片后，如果上方箱子里还有唱片，唱片机会再次自动取片并播放。如果装置通过取出唱片停止播放，就需要同时控制上方箱子的供片。
