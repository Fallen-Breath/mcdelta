# 报告写作要求

本文整理报告写作方面已确认的要求及其原因，供维护分析指引时参考。分析任务所需的指令由 `prompts/snapshot_analysis_worker.md` 独立提供。

## 内容范围

- 面向熟悉 Minecraft 的读者，说明更新对已有机制、玩法、操作和装置表现的影响。新增内容在影响已有机制时纳入。
- 收录能够说明触发条件及新旧表现差异的修改。底层代码的间接影响也需要追踪到游戏表现。
- 文案、翻译和贴图修改无需关注。没有符合范围的变化时，简要说明，无需凑写条目。
- 分析范围保持通用，避免围绕某次漏报反复添加专项补丁。

这些要求用于确定报告收录什么，避免将源码改动或更新日志直接当作游戏表现变化。

## 基础信息与条目组织

- 开头使用简单、固定的格式列出上一个版本和当前版本。
- 正式报告的文件名和基础信息无需展示 Guardian 的提交哈希；代码链接可以包含哈希。
- 按游戏机制组织条目，同一机制的相关变化放在一起。标题概括修改主题，避免将每条现象或结果都单列成章节。
- 多项简单修改只有共享具体机制或使用场景时才合并，避免用宽泛主题收拢关联不强的内容。
- 根据变化对已有玩法的实际影响排序，考虑影响范围及对既有用法的后果。分类优先级仅作排序与篇幅分配的参考，无需逐类覆盖或按分类组织报告。
- 根据解释需要决定篇幅。代码量少的重要变化可以靠前且简述，复杂修改可以充分展开。

条目的主题、排序和篇幅各有判断依据。完整展开的条目与简述条目可以交错出现，避免模板的展示顺序变成重要性排序。

## 条目结构

- 完整展开的条目先简要介绍涉及的机制及本次变化，再依次说明差异出现的场景和版本变化；需要时添加实际影响，最后附代码出处。
- 引入段提供背景，场景说明触发条件，两者作用不同。
- 版本变化明确说明相同条件下的旧版和新版表现。补充工作方式时注明版本归属，避免读者自行推断。
- 单项简单修改可以用短段落说明；具有共同主题的多项简单修改可以用列表合并简述。简单修改无需套完整栏目。
- 复杂内容在对应栏目内展开，保持栏目稳定，避免随意增设小标题或将内容挤进一个长段落。

结构应当帮助读者辨认背景、条件、差异和后果，同时允许不同复杂度的修改采用适当篇幅。

## 信息取舍与实际影响

- 先确定每项修改最值得说明的版本差异，再选择解释它所需的信息。
- 背景、原理和未发生变化的行为，仅在帮助理解本次差异时保留。
- 多个事实需要说明关系，让读者辨认主要变化、必要解释和后果。将分号换成列表，仍可能是在堆砌事实。
- 实际影响只展开值得单独解释的直接后果。版本对比已表达充分时，省略该栏目；有一句值得补充时，就只写一句。
- 不为填满栏目额外编写装置建议、操作提醒或改造方案，也不重复新旧表现。
- 不延伸说明其他无关执行路径，或补充本次变化没有涉及的问题。

例如，一项修改增加了异常后的断线处理，报告无需因此额外讨论已完成的世界修改是否回滚。该事实与本次差异的关系不足以支持单独补充。这类案例用于解释取舍原则，不构成针对特定机制的分析要求。

## 结论、条件与依据

- 条件和必要的适用限制写在对应结论附近，影响范围与源码及相关数据支持的范围一致。
- 对影响结论的疑点尽可能查清。确实复杂到需要超出任务的专项研究或实验时，才留下具体的未决问题。
- 已确认事实与推断在对应位置区分，不添加通用的验证状态声明。
- 条目末尾提供对应版本的源码或数据出处，能追溯到相关实现。
- 配置 GitHub 仓库地址时，引用对应版本提交中的文件及行号；否则使用源码根目录下的相对路径和行号，路径使用 `/`。

报告需要能够核查的结论与出处，无需展开调查过程。

## 语言表达

- 用自然语言说明游戏中的对象、动作、条件和结果，正文无需穿插用于复述实现的代码标识符。
- 避免将代码概念逐字翻译成生硬中文。游戏名称使用已确认的官方译名，无法确认时保留原名。
- 不自行编造术语或省略必要成分来追求简短。句子应当明确动作涉及的对象，指代和条件衔接应清楚。
- 机制描述明确所属版本，并交代它如何解释本次差异或影响，避免孤立描述一组现象。

例如，将 `neighbor` 单独译成“邻居”会让读者依靠中译英猜测含义；“向相邻方块发出更新”能直接说明游戏行为。“唱片播放结束时”也比自行缩写成“曲终”更清楚。

“通顺、完整”不足以代替这些要求。模型需要明确知道应保留哪些对象、关系和条件，而不能依赖本次对话理解一句笼统的评价。

## 叙述与排版

- 客观、直接地陈述版本变化，避免反问、设问、自问自答及调查故事。
- 避免通过纠正假想误解介绍变化；否定表达在确实说明版本差异时使用，避免无来由地引入对比。
- 调查经过、核查记录、通用验证状态和没有具体信息的建议无需写入正文。
- 新旧版本使用无序列表，版本标签无需加粗。加粗仅用于少量必要强调。
- 不默认用表格容纳新旧表现，长内容容易在表格中变得难读。
- 列表用于表达并列关系，不能代替事实之间的组织；避免长段落拼接大量事实，也避免过度切分小标题。

## 分析指引与示例的分工

- 分析指引应当独立表达必要的写作要求，不能假定执行模型读过这段讨论。
- 格式模板规定组织结构，内容示例帮助理解一篇报告如何组成。两者分开提供。
- 示例中的版本、修改与出处仅供参考，不能成为实际分析目标或事实依据。
- 保留能够影响模型写作选择的明确要求，整理重复表达；避免不断叠加针对个别错误的禁令，也避免为了省字删掉必要说明。
